## 1. 我们是谁 / 项目定位

**一句话**：ai-video-studio 不是「又一个剪辑软件」，而是「**AI 可调用视频操作系统**」——把剪辑能力封装成 AI Agent 能直接驱动的视频 DSL，人也能手动精修。

**主线双线（用户创业方向）**：
- ① 内容生意：AI 工具信息差 → 内容 → 部署变现（最高优先级产品「画面思维·反推提示词」教学）
- ② AI 剪辑工作台（本项目）：造「AI 可调用视频操作系统」，非造剪辑软件壳

**护城河**：Video DSL（Operation Schema ↔ Timeline Schema 经 Command 桥接；Agent 永不直接碰 Timeline）。这是 OpenCut / 剪映都还没做成「AI 可编程」的点。

**对标对象**：OpenCut（web 版，TS/React，85.4k⭐️）—— 我们路 C 的编辑行为规格以它为参照，但**数据模型不换**（保留剪映 `draft_content.json` 资产），只重做「编辑逻辑的实现方式」。

## 2. 我们怎么做的（技术路线与关键决策）

**技术栈**：纯 Python + PyWebView（弃 Electron）；前端原生 JS（player.js / media.js / renderer.js / timeline.js 已抽离独立）；剪映草稿 = 文件夹 + `draft_content.json`（materials / tracks / segments，时间单位微秒，`seg_id`≠`material_id`）。

**ADR-001 架构冻结（2026-08-15，决策冻结非代码全落地）**：
- 播放器 + 时间轴 = 基础设施
- Operation Schema ↔ Timeline Schema 经 **Command** 桥接（Agent 永不直接碰 Timeline）
- **两层导出（目标架构，非已交付）**：① 导剪映草稿（`pyJianYingDraft`，已通）② 直导 MP4（**尚未存在**，必须自研渲染器，绕不过）。→ **当前不存在「AI 自动出片闭环」**：AI 能驱动编辑并导剪映草稿，但最终出片仍依赖剪映渲染。文档若读到「两层导出」须理解为路线目标，不是可交付能力。

**路 C 决策（2026-08-28 拍板，覆盖旧「M 系列先行」）**：
- 数据模型不换（保留剪映资产），只重做编辑逻辑实现
- **不抄 OpenCut 代码**，照搬其行为规格用剪映模型重实现
- 否决路 A（换模型对齐 OpenCut）：剪映特效是「特效 ID + 参数」体系，翻译不过去，会自断剪映高级能力
- 垂直切片代替水平分层：能力块从头做穿（预览→落库→导出→参数面板→MCP），避免层间断层

**已完成的大块**：
- R3 重构 69 张卡全部落码（2026-08 初）
- UI 改造 P0–P6 全部收口（换肤 / 尺寸%化 / 去文字标签 / 素材库 / 时间轴规格 / 播放器规格 / 参数面板动态 tab）

## 5. 对标 OpenCut：我们还差多少

### 5.1 作为「纯人工剪辑编辑器」比 OpenCut 差多少
**OpenCut 领先**：更成熟的 web 原生多轨时间轴、转场、滤镜、文字、自动字幕；浏览器协作、ffmpeg.wasm 直出，零安装。
**我们领先 / 差异化**：**剪映 `draft_content.json` 原生兼容**（国内硬需求）；离线优先、本地工程；两层导出（剪映草稿可继续精修 + 目标 MP4）；编辑逻辑已对齐 OpenCut 行为规格。
**结论**：纯手动维度 OpenCut 功能完整度领先，我们赢在剪映兼容+离线+双层导出（不同楔子，不正面竞争）。

### 5.2 作为「AI 编辑器」比 OpenCut 差多少
**我们的差异点（OpenCut 没有）**：MCP 机制 + Command API + Video DSL——Agent 可编程驱动剪辑（护城河）。
**我们的缺口**：
- **直导 MP4 自研渲染器未做**（目标架构，当前只能导剪映草稿靠剪映渲染；纯 AI 自动出片闭环不存在）
- 真实 AI 智能剪辑能力近乎空白：自动粗剪 / 智能重构图 / 自动字幕 / 语音口型 / 素材自动匹配
- 渲染合成层残缺（`blend_mode` 能设能落盘但 renderer 不消费，见 §6）
**结论**：AI 编辑器维度我们有「架构骨架 + 入口」，但「智能」与「自研渲染」是两块硬骨头；OpenCut 同样没做成 AI 可编程，这是超车窗口也是当前最大短板。

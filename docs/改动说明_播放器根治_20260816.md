## 三、本次修改（8-16 详细，重点看这里）

### 3.1 决策过程（双 AI 审查后拍板）

**根因分析**（审计文档：`docs/audits/playback-rootcause-architectural.md`、`timeline-to-playback-dataflow.md`）：

```
OpenCut（参考开源剪辑器）：媒体只听墙钟，自己调度自己
  → 音频 Web Audio lookahead 提前 2s 调度，到点出声（无状态机）
  → 视频 canvas 逐帧抽帧（元素只是解码器）
  → 跨段 = 调度器自然衔接，没有"切换"动作

我们：媒体元素自己 play/pause/seek（状态机）
  → 跨段要同元素 seek + play（元素状态参与判断）
  → 元素状态机和墙钟打架 = 竞态 = 卡/无声
```

**根治方案**：`docs/architecture/playback-rootfix-bundled.md`（v1.3，经 3 轮独立 Agent 审查）——建立 **Playback Graph 语义层**（唯一换算点），音频迁 Web Audio，视频跨段销毁重建。6 个 Phase 原子切换，统一验收 V1-V6。

### 3.7 当前卡住的问题（请 GPT 重点审）

**现象**（用户真机日志）：播放 17s 项目（3 视频段 + 3 音频段，各 5s 间隔 1s）：

```
[seek] VIDEO to=0.210 cur=0.000   ← 每 200ms 一次 seek（drift 节流）
[seek] VIDEO to=0.411 cur=0.000
...
[seek] VIDEO to=4.866 cur=0.150   ← 播放头走了 4.8s，元素 cur 只走了 0.15s（~3% 速度）
[mediaEvent] video:? playing      ← 448 次 playing 事件
[PAUSED-DIAG] us=17.012s maxUs=17.000s videoSegs=3 audioSegs=3   ← 前端数据正确
```

**推断**：drift 机制（"媒体落后播放头 >100ms 就 seek 回正确位置"）在元素 seek 后需要缓冲时（WebView2 常见）会**每 200ms 打断缓冲** → 元素永远追不上 → 死循环。这可能是"媒体元素极慢播放"的根因。

**待落码的根治方向**（尚未实施，想请 GPT 验证）：
```
drift 加"seek 静默期"：一次 seek 后 1s 内不再 seek 同一元素（给缓冲时间）
mediaClockReady 重试：800ms → 2.5s，且依赖元素 playing 事件而非盲目重试
```

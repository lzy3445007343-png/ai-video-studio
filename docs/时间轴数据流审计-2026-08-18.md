# 时间轴完整数据流审计 — 底层根因诊断（2026-08-18）

> 目的：全面审计"素材库拖入 → 时间轴渲染 → 段拖动/换轨 → 后端落盘 → 回填渲染"整条数据流，
> 找出"换轨改一下午没改好 / 偶发素材放不进 / 拖不动"的**底层**根因（不是交互表现）。

---

## 1. 完整数据流（每一跳都核对过代码）

### ① 素材库拖入（HTML5 drag）
```
卡片 dragstart ──▶ dragGhostData 缓存（WebView2 dragover 读不到 dataTransfer，用全局变量绕开）
                ├─ window.__dragStartY（落点方向判定）
                └─ setData("text/plain", {name,path,type})
timeline dragover ──▶ computeDrop(e, wantType, vDir, atTimeUs, isLibrary=true) → {kind: existing|new}
                ├─ 写 __libDropCache（防松手边界漂移）
                └─ 反馈：目标轨高亮 / 临时新轨 / dropLine
drop(onTimelineDrop) ──▶ call("add_to_timeline", name, path, type, dataTi 或 null, atTimeUs, insertIndex)
后端 add_to_timeline ──▶ _ensure_track/_insert_track → 段写入 → save_state 落盘 draft_state.json
前端 .then(refresh) ──▶ call("get_state") → 回填 Store.draft → renderAll → buildTracks → renderTimeline
```

### ② 时间轴内拖段（pointer events）
```
mousedown(startPointer) ──▶ pendingDrag{ key:"type:ti:idx", s0(段的完整快照), startMouseX/Y }
mousemove(onPointerMove) ──▶ d.curLeftUs（X 位置）
                        ├─ computeDrop(e, type, vDir, curLeftUs, isLibrary=false) → d.targetKind/targetDataTi/dataInsertIndex
                        ├─ Store._emit() → renderTimeline（被拖段实时显示目标轨/临时新轨）
mouseup(onPointerUp) ──▶ call("relocate_segment", type, ti, idx, to_ti, curLeftUs, insertIndex)   ← new=建轨+移段
                        ├─ 或 call("move_segment", ...) / move_group / update_effect
                        └─ .then(refresh) → get_state → Store.draft → 重渲染
```

### ③ 后端写路径（所有写命令都走）
```
Api 命令 → self.draft 原地修改 → [_collapse_empty_tracks(draft)]（8 个命令触发）→ save_state → 落盘
```

## 2. 底层根因（按严重度排序）

### 🔴 R1：全链路引用 = `(type, ti, idx)` 位置序号，`ti` 是脆弱的"当前显示第 N 条该类型轨"

- 前端：`dataset.key = "type:ti:idx"`、`selectedKey`、`drag.key`、`segGeom` 匹配、`selectAll` 全用 ti
- 后端：`_track_segs(type, ti)` 用 ti 定位（ti 换算成 overlay 数组中"该类型第 N 条"）
- **问题**：`ti` 不是稳定引用。**任何增删轨 / 折叠 / 新建轨都会让 ti 编号整体漂移**。
  - 拖动中 mousedown 记下的 `d.key`（旧 ti）与 renderTimeline 重新编号后的 ti **不一致** → 被拖段不跟手 / 落位定位错 / 选中指向错段
  - 折叠后 selectedKey 指向错误段 → 删除/特效/关键帧作用到**错误的段**
  - **这解释了全部"偶发"现象**：大多数时候拖动中 overlay 不变 → ti 稳定 → 正常；一旦拖动中后端触发折叠/新建（如 move 后 collapse），ti 漂移 → 偶发失败

### 🔴 R2：`_collapse_empty_tracks` 在 8 个写命令里触发，任何操作都可能改 overlay 数组结构

- 调用点：remove_segment / remove_segments / duplicate / toggle_source_audio / move_segment(ripple) / move_group / relocate_segment / scale_group
- **问题**：折叠删除空轨 → overlay 数组长度/顺序变 → 前端 buildTracks 重新编号 ti → **所有存量 ti 引用（选中态/拖动态）瞬间失效**。换轨（relocate）自身就触发折叠 → 换轨后 ti 全变 → 后续操作错位。

### 🟡 R3：拖动与 500ms 轮询的时序

- 拖动中跳过 refresh（`!Store.state.drag`）✓；但松手 → `Store.set({drag:null})` → 提交 call + `.then(refresh)` 与 500ms 轮询**可能并发** get_state → 两次回填（内容一致，风险低，但渲染时序可能乱）

### 🟡 R4：MP4"松手消失"的具体路径（已修一半）

- ① 落隐藏轨（CSS track-hidden → 不可见）→ 已加"命中隐藏轨→新建轨"（commit 82325f1）
- ② 若拖动中 overlay 变 → computeDrop 算出的 dataTi 与提交时实际 overlay 不一致 → 段进错轨 → 折叠可能把它并入/删除 → 消失

## 3. OpenCut 对照（为什么 OpenCut 没有这些 bug）

| 维度 | OpenCut | 我们 |
|---|---|---|
| 引用 | **稳定 id**：trackId/elementId（uuid）全链路使用 | **(type, ti, idx) 位置序号**，ti 随结构漂移 |
| 数据更新 | immutable（每次返回新 SceneTracks）| 原地修改 draft + 折叠 |
| 拖动预览 | previewElements 改元素 trackId（引用不变）| 每帧重编号 ti + key 匹配 |
| 提交 | MoveElementCommand（建轨+移段原子，引用稳定）| relocate_segment（原子，但 ti 是位置）|

**结论：OpenCut 用稳定 id 把"显示位置"和"数据引用"解耦；我们用位置序号当引用——结构一变化就全乱。这是"改一下午改不好"的底层根因。**

---

## 4. 修复方案（分级）

### 方案 A（根治，大重构）：全链路改稳定 id
- 轨道引入稳定 `tid`（uuid，初始化时生成，落盘持久化）
- 前端 key = `tid:segid`；后端命令签名 `(tid, segid)`
- 折叠/undo/导出适配
- **工作量**：大（前端 key 全换 + 后端 70 个命令签名全换 + 迁移），2-3 天

### 方案 B（推荐，中重构）：引用改段 id，命令仍用 (type,ti,idx)
- **前端拖动/选中/渲染匹配 全部改用 `seg.id`（段已有稳定 uuid）**：
  - `d.segId`（mousedown 记段 id）替代 `d.key` 匹配 segGeom / 被拖段显示
  - selectedKey 改存 `seg.id`（或 key 解析时用 id 定位段，不再用 ti）
  - segGeom / renderTimeline 用 segId 匹配被拖段
- **后端命令提交时**仍传 (type, ti, idx)（提交那一刻索引有效即可，refresh 后自愈）
- 折叠/新建轨不再影响拖动与选中（引用是 id，不随 ti 漂移）
- **工作量**：中（前端 key/匹配逻辑改造，后端不动），半天

### 方案 C（表现层）：只修跟手/蓝线/反馈
- **已被证明不够**（6 轮迭代验证：表现修好，偶发/消失/拖不动依旧）

**我的判断：B 是"换轨改一下午改不好"的真正解药**——它消除"ti 漂移导致引用失配"这个偶发根源，且不动后端签名、不迁移数据。

# AI-Native 视频编辑平台架构圣经（v2）

> **文档性质**：未来架构蓝图（Architecture Blueprint）。回答一个问题——**"如果我们要从零构建一个 AI 可调用的视频编辑操作系统，架构应该长什么样？"**
> **设计基准**：《OpenCut 架构圣经 v1》（`opencut-架构圣经-v1-2026-08-22.md`，908 行，源码实证）——这是我们的"标准底座"，本蓝图在其之上扩展，不复刻、不推翻，只做三件事：**复用 OpenCut 已验证的底座，替换我们已暴露的结构性债务，新增 AI 原生需要的 8 个系统**。
> **现实基础**：ai-video-studio 现有——后端 Command API（90+ 命令）+ MCP server + 审计日志 + 剪映草稿导出 + 本地 Whisper 字幕 + Property/Interaction/Command/Subscription 四内核。
> **版本日期**：2026-08-22
> **一句话定位**：**视频编辑的本质是"一份 Document 被一条命令流反复改写"；AI 原生平台的本质是"AI 生成这份 Document 和这条命令流，而不是操作 UI"。**

## 0. 全局结论（TL;DR）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **Document 是唯一事实来源**，UI/渲染/导出/AI 全部是 Document 的投影。这是 OpenCut"ScenesManager 是唯一写入口"的极端化。 | OpenCut 圣经 §1.1 / §4.2 |
| 2 | **一切可撤销编辑 = 一个自包含 Command**，AI 生成的也是 Command。撤销=整轨快照还原。 | OpenCut 圣经 §1.8 / §1.9 |
| 3 | **8 个新系统不是 8 个孤立模块**，而是一条链：`Plugin 注册一切 → Preset 是插件的复合 → Semantic 给 Document 加 AI 语义 → Resource Graph 索引语义 → Intent Layer 编排全部 → Document 落地 → Render Graph 渲染`。 | 本文 §3 |
| 4 | **我们最大的 AI 优势（后端命令 + MCP）要保留**，6 项结构性债务（D1–D6）在 Phase 1/2 逐一消解。 | 《系统架构总览》§三 / §四 |
| 5 | **Document Protocol 用 JSON**（不是二进制、不是 XML）——因为 AI 要能读、能生成、能 diff、能迁移；剪映草稿已是 JSON，导出侧天然兼容。 | 本文 §3.1 |
| 6 | **Intent 粒度 = 语义级目标**（"前 3 秒 hook"），不是命令级（"addEffect"）也不是自由文本。Intent 是 LLM 与引擎之间的契约。 | 本文 §3.6 |
| 7 | **协作粒度 = Command 级 Operation Log**，冲突解决 = 版本向量 + 命令级 merge。 | 本文 §3.7 |
| 8 | **渲染 = 固定 6-Pass Render Graph**（Video→Mask→Effect→Color→Composite→Output），未来 LUT/AI 增强/超分 = 新增 Pass，不动管线骨架。 | 本文 §3.8 |

## 1. 架构原则（0.5 章）

四条原则是**设计约束**，不是建议。任何系统设计违反其中之一即为设计错误。每条原则给出"为什么"（对 AI 平台的价值）与"怎么落地"（具体机制）。

### Principle 1：UI 不是事实来源（UI → Controller → Manager）

**为什么**：OpenCut 审计已经证明——硬编码在 UI 的交互（画布视口缩放、吸附指示、面板布局）没有任何程序化入口，AI 无法驱动它们（OpenCut 圣经 §5.1 类别 C）。一个 AI 原生平台里，**凡是 AI 需要触达的能力，就不能只存在于 UI 层**。UI 必须是"最薄的一层"：只负责把用户手势翻译成对 Controller/Manager 的调用，自身不持有任何领域状态、不直接修改 Document。

**怎么落地**：
- 分层强制：`UI 事件 → Interaction Controller → EditorCore Manager → Command → Document`。UI 组件只读（订阅 Document 投影），写一律走 Manager 方法。
- 规则：**任何 UI 组件里出现 `document.timeline.xxx = ...` 这种直接写领域状态的代码，就是架构违规**，代码评审一票否决。
- 我们已有四内核中 C2 Interaction Kernel 就是这个 Controller 层——保留并统一化，让所有交互都进 Controller，禁止在 React 事件回调里直接写状态。

### Principle 2：所有用户意图必须 Command 化

**为什么**：撤销/重做、审计日志、协作广播、操作恢复、AI 回放——全部依赖"每次修改都对应一个自包含 Command"这一前提。OpenCut 的 Command 模型（自包含对象：execute 保存 savedState、undo 整轨还原、BatchCommand 原子组合）已被验证是正确且简单的（OpenCut 圣经 §1.8/§1.9）。AI 生成的编辑动作天然就是 Command 序列，所以**命令化是 AI 可操作性的前提**。

**怎么落地**：
- 任何领域状态修改**必须**经由 `Command` 对象执行，直接调用 Manager 写方法但没有 Command 包裹 = 架构违规。
- Manager 语义 API（`timeline.moveElements()` 等）内部也必须构造 Command——OpenCut 已经这么做，我们后端 Command API（90+）也是命令化的，两端对齐。
- 命令是**审计单位**、**撤销单位**、**协作广播单位**、**AI 回放单位**——同一个对象四个用途，这是内聚的关键。

### Principle 3：状态分三层（Persistent 正式 / Transient 预览 / UI 界面）

**为什么**：OpenCut 的 previewOverlay 草稿层已经证明：拖动中每帧写正式状态会导致"一帧一历史"，必须用草稿层折叠成一次 commit（OpenCut 圣经 §4.2）。AI 平台还要再加一层——**AI 批量操作时的中间态**不能污染 Document，也不能污染撤销栈。三层的边界是正确性的关键。

**怎么落地**：

| 层 | 内容 | 谁写 | 是否落盘 | 是否进历史 |
|---|---|---|---|---|
| **Persistent（正式）** | Document：timeline/assets/semantic... | Manager（经 Command） | ✅ | ✅ |
| **Transient（预览）** | previewOverlay、渲染中间帧、AI 批量操作前的 staging | TimelineManager.previewElements() / IntentLayer.stage() | ❌ | ❌ |
| **UI（界面）** | 视口缩放、滚动位置、面板布局、选中高亮 | UI 组件本地 state | ❌ | ❌ |

- Transient 层对 AI 特别重要：**AI 执行一个 10 步计划时，先全部写入 Transient staging，全部成功后一次性 commit 成 N 条命令入栈**；任一步失败则 discard，Document 完全不受污染。
- 读取规则沿用 OpenCut：渲染层永远读"Transient 优先"（`getPreviewTracks() = previewTracks ?? committed`）。

### Principle 4：AI 只能操作 Intent，不操作 UI（最重要）

**为什么**：如果 AI 通过 UI 操作（模拟点击、调 viewport）来做视频，那它就退化成一个"手速很快的用户"，既慢又脆。AI 的价值在于**表达语义意图**，引擎负责把意图翻译成精确的命令序列。反过来，如果 AI 直接下发命令（`addEffect`），那它就得自己懂编辑器所有细节——LLM 会出错，而且命令级别的编排不可复用。

**怎么落地**：
- 强制分层：`AI Agent → Intent Layer → Planner → Command Generator → EditorCore`（见 §2 架构图）。
- AI 的输出契约是 `AIIntent`（结构化意图对象），**不是** Command，**不是** UI 操作。
- 兜底规则：**AI 请求最终必须落到 Command 层**——任何 AIIntent 都无法绕过命令层直接写 Document。这条规则同时保证：AI 的操作天然可撤销、可审计、可协作广播。
- "AI 不操作 UI"不是"AI 看不到 UI"——AI 可以**读取**渲染结果（截图）、读取 UI 状态，但**写**只走 Intent。

**关键协作场景**（体现内聚）：
- **插件注册 Preset**：`PluginManager.registerPlugin(plugin)` 注册一个 `PresetDefinition`，Preset 进入 `PresetManager` 的注册表；Intent Layer 的 Planner 按 `applyPreset("xiaohongshu-hot")` 查表。
- **Semantic 被 Resource Graph 索引**：SemanticManager 对元素打 `ObjectReference`（"这个人叫小明"），ResourceGraph 把 `asset → element → annotation` 连成边，AI 才能问"小明在哪出现过"。
- **Preset 引用 Semantic 模板**：Preset 的 `semantic` 字段声明"这个模板的 hook 段标注 StoryBeat.type='hook'"，apply 时 SemanticManager 自动补标注。
- **Intent 消费 Resource Graph**：Planner 要"找一个人物的所有镜头"，直接 query ResourceGraph 而不是扫 Document。
- **所有变更进 Operation Log**：Command 执行时同时发 `EditorEvent` 到 EventBus 并写 OperationLog——AI 回放、协作、审计三个场景读同一条日志。

### 3.1 Document Schema Protocol（工程文档协议层）

**为什么需要它**：OpenCut 的 `TProject` 是运行时的内存结构 + 序列化快照（metadata/scenes/settings/version），它**没有把"文档格式"作为一等公民**——没有独立于运行时模型的协议定义。AI 原生平台的本质是 **AI 生成项目 = 生成协议文档再加载，而不是操作 UI**（背景要求第 1 条）。所以我们必须回答："工程文件是什么协议？"。OpenCut 的版本迁移（v0→v28）证明格式会演进，所以协议必须自带 `schemaVersion` 与迁移管线。

**决策**：**Document Protocol 用 JSON + JSON Schema + 版本化迁移**。不用二进制（AI 无法生成/ diff / 审查）、不用 XML（臃肿且剪映已是 JSON）。理由：
1. AI（LLM）读 JSON 和写 JSON 的能力最强，二进制对 LLM 是黑盒；
2. 剪映草稿导出已是 JSON，我们导出侧天然兼容；
3. JSON 可 diff → 协作冲突解决、审计对比、AI 增量修改全部可行；
4. 迁移管线（schemaVersion 逐版升级）OpenCut 已证明可行（v0→v28）。

**数据模型**：

```ts
// doc-protocol/schema.ts —— 文档协议定义（JSON Schema 生成 + TS 类型）
export interface VideoDocument {
  schemaVersion: number;                       // 协议版本，默认 2。每次不兼容变更 +1，带迁移器
  metadata: DocumentMetadata;                  // id/name/description/author/orientation(竖屏|横屏)/
                                               // duration/fps/createdAt/updatedAt/tags
  assets: AssetNode[];                         // 素材注册表（媒体 + 引用）
  timeline: TimelineDocument;                  // 场景/轨道/元素（OpenCut TProject.scenes 升级）
  animation: AnimationRegistry;                // 全局动画通道/预设的声明（可选，bindings 在元素内）
  plugins: PluginRef[];                        // 本工程依赖的插件清单（含版本）
  extensions: ExtensionData[];                 // 插件自定义数据（keyed by pluginId，防冲突）
  history?: DocumentHistory;                   // 可选：文档级操作历史（跨会话恢复/回放）
}

export interface TimelineDocument {
  scenes: SceneDoc[];                          // 场景列表（含 main scene）
  currentSceneId: string;
  settings: { fps: FrameRate; canvasSize: [number, number]; background: string };
  timelineViewState?: TTimelineViewState;      // zoom/scroll 等 UI 态，落盘但不算领域状态
}

export interface SceneDoc {
  id: string;
  name: string;
  isMain: boolean;
  tracks: SceneTracks;                         // overlay/main/audio，结构与 OpenCut 完全一致
  storyBeats: StoryBeatRef[];                  // ★ 语义层挂载点（见 §3.4）
  semantic: SceneMeaningRef;                   // ★ 场景语义标注（见 §3.4）
}

// 资产统一用 id 引用，杜绝位置索引（解决我们的 D1 债务）
export interface AssetNode {
  id: string;                                   // 全局唯一 id（UUID）
  kind: "media" | "url" | "generated";          // 本地文件/远程/程序生成
  media?: MediaAsset;                           // media 时复用 OpenCut MediaAsset
  url?: string;
  status: "ready" | "processing" | "error";
}
```

**关键接口**：

```ts
export class DocumentManager {
  createDocument(spec: DocumentSpec): VideoDocument;          // AI 生成项目的入口
  loadDocument(raw: unknown, opts?): Promise<VideoDocument>;  // 校验 + 迁移 + 装配
  saveDocument(doc: VideoDocument): Promise<void>;            // 落盘（复用 SaveManager 防抖）
  migrateDocument(doc: {schemaVersion:number}, from: number, to: number): VideoDocument;
  validateDocument(raw: unknown): ValidationResult;           // JSON Schema 校验
  generateDocument(prompt: string, assets: AssetRef[]): Promise<VideoDocument>; // ★ AI 直出文档
  snapshot(): VideoDocument;                                  // 供渲染/导出/AI 读取
}
```

**与 OpenCut v1 衔接**：
- **复用**：`TProject` 的 scenes/settings/version 结构（§1.2），`MediaAsset`（§1.6），`MediaTime`/`FrameRate`（§3.4）。时间、轨道、元素模型**一字不改地继承**——因为它们是已验证的正确底座。
- **扩展**：`metadata` 增加 orientation/tags/author；新增 `assets`/`plugins`/`extensions`/`animation` 四段；`scenes` 每场景挂 `storyBeats`+`semantic` 钩子。
- **替换**：OpenCut 的 `TProject` 不是协议（它是运行时类型）；我们的 Document 是**协议 + 运行时同源**（类型生成自 schema）。这是本质区别：AI 生成 JSON → 加载器校验/迁移 → 直接变成运行时状态。

**落地阶段**：Phase 1（见 §6）。

### 3.2 Plugin / Extension System（插件系统）

**为什么需要它**：OpenCut 的 effects/masks/graphics 是**内置注册表**（`registerDefaultEffects` 写死在启动时，OpenCut 圣经 §3.2），不是插件。我们要让 effects/masks/graphics/text/stickers **从内置注册变成 Plugin API**（背景要求第 2 条）。插件可注册 5 种能力：Command / Effect / AnimationPreset / Panel / Exporter。插件系统是 Preset 系统和 Render Graph 扩展的**注册通道**——Preset 是插件的一种复合体，渲染 Pass 也是插件。

**决策**：**Plugin = 静态 manifest 声明 + 代码实现**。manifest 描述"这是什么、注册什么"，代码实现具体逻辑。运行时加载（非编译期），支持启用/禁用/版本化。**所有可扩展点统一进 PluginManager 一个注册表**，不再有各自独立的 registry（OpenCut 的 effectsRegistry/masksRegistry/graphicsRegistry 全部收敛进来）。

**数据模型**：

```ts
// plugin/plugin.ts
export interface PluginManifest {
  id: string;                    // 全局唯一，如 "studio.subtitle-pop"
  version: string;               // semver
  name: string;
  description: string;
  registers: {
    commands?: CommandDefinition[];        // 新命令：{id, schema, handler(executor)}
    effects?: EffectDefinition[];          // 特效定义（复用 OpenCut EffectDefinition）
    masks?: MaskDefinition[];              // 蒙版定义
    animationPresets?: AnimationPresetDefinition[]; // 动画预设（给 Preset 系统用）
    graphics?: GraphicDefinition[];        // 图形
    stickers?: StickerDefinition[];
```

### 3.3 Preset / Template 系统（预设模板层）

**为什么需要它**：一个"爆款视频模板"不能是 100 个 keyframe——那是实现细节，不是模板。**模板的本质是"风格 + 动画配方 + 节奏骨架"**（背景要求第 3 条）：`Preset { style, animation: [subtitle-pop, zoom-in...], timing: [hook 0-3s, body 3-30s, CTA 30-40s] }`。AI 只需 `applyPreset("xiaohongshu-hot")`，引擎负责展开成具体命令。这是 Intent Layer 的"食材库"——没有 Preset，AI 每次都要从零生成 100 个 keyframe，既慢又不可复用。

**决策**：**Preset = 声明式配方，不是命令序列快照**。它描述"要什么效果/风格/节奏"，由 `PresetResolver` 在 apply 时展开成命令计划。Preset 内部引用动画预设（来自 Plugin 注册的 animationPresets），并可携带语义标注模板。

**数据模型**：

```ts
// preset/preset.ts
export interface PresetDefinition {
  id: string;                      // "xiaohongshu-hot"
  name: string;
  kind: PresetKind;                // "video-template" | "text-style" | "transition" | "style-pack" | ...
  categories: string[];            // ["小红书", "知识", "爆款"]
  // ① 风格：作用于 Document 的全局/局部样式参数
  style: {
    colorPalette: string[];        // 主色
    fontFamily?: string;
    textStyle?: TextStylePreset;   // 字幕样式
    canvasOrientation?: "portrait" | "landscape";
    filter?: { effectId: string; params: ParamValues };  // 全局滤镜

  // ② 动画配方：引用插件注册的动画预设（不是内联 keyframe）
  animation: AnimationPresetRef[]; // [{id:"subtitle-pop", targets:"text"}, {id:"zoom-in", targets:"main"}]
  // ③ 节奏骨架：hook/body/cta 的时间结构（秒，相对项目时长）
  timing: TimingGuide;
  // ④ 语义模板：apply 时自动打语义标注（衔接 Semantic 层）
  semantic?: SemanticPresetTemplate;
  tags?: string[];                 // AI 搜索用
}

  tempo: "slow" | "normal" | "fast";        // 节奏密度
}

  semanticPlan: SemanticAnnotationPlan[]; // 待打标注清单
```

**关键接口**：


**与 OpenCut v1 衔接**：
- **复用**：OpenCut 的 `GraphicElement`（definitionId + params 模式，§1.5）、`ParamDefinition`（§3.2）、`buildDefaultParamValues`（§3.2）——Preset 的 style/params 就是这套机制。
- **扩展**：OpenCut 只有"元素级定义"（graphic/effect/sticker 是单个定义）；Preset 是**组合级定义**（风格+动画+节奏+语义四元组），是新的抽象层级。
- **替换**：OpenCut 没有任何模板概念。`applyPreset` 内部展开时复用它全部的元素/动画/命令机制。

### 3.4 Semantic Layer（语义层）

**为什么需要它**：AI 要理解"这段是 hook""这个人叫小明""这里是情绪高点"，但 Document 里只有 `TextElement`/`VideoElement` 这些**语法层**对象（背景要求第 4 条）。语义层把 Document 的语法结构映射成 AI 可读的**语义视图**：角色/地点/情绪/重点/节奏/故事节点。**Semantic 是 AI 的"文档注释"**——它不改变编辑行为，只让 AI（和未来的智能功能）能问"为什么这里这么剪"。

**决策**：**Semantic 是 Document 内的第一等公民（挂在 scene/element 上）**，不是运行时推导（推导不可持久化、AI 每次都要重算）。但标注可以**由 AI/算法自动生成**（Whisper 转写 + LLM 分析 → 生成标注），人类/AI 编辑时可增删改。

**数据模型**：

```ts

export interface ObjectReference {
  id: string;                          // 语义对象 id，如 "character:xiaoming"
```

- **替换**：不加新轨道、不改渲染——语义层**只挂在 Document 上**（SceneDoc.storyBeats/semantic、element 的 annotations），零侵入。

### 3.5 Resource Graph（资源关系图）

**为什么需要它**：AI 要能回答两个高频问题——**"这个人物在哪出现过"**（ObjectReference → 关联元素 → 素材）和 **"删这个素材影响什么"**（Asset → UsedBy → Element → Animation → Effect → Preset → Annotation）。Document 是**树**（scene→track→element），回答这两个问题需要**跨树关系**（背景要求第 5 条）。Resource Graph 是 Document 的**关系索引**。

**决策**：**Resource Graph 是派生数据（derived view），不是独立持久化状态**。每次 Document 变更时增量重建（或按需重建）。好处：不会有"图与文档不一致"的 bug；Document 是唯一事实来源（符合 Principle 1）。

**数据模型**：

```ts
// resource-graph/resource-graph.ts
export type GraphNodeType =
  | "asset" | "element" | "animation" | "effect" | "mask"
  | "preset" | "annotation" | "semantic-object" | "scene" | "track";

export interface GraphNode {
  id: string;

  ref: string;                 // 指向 Document 里对应对象的 id
  name: string;
  meta?: Record<string, unknown>;
}

export type GraphEdgeType =
  | "usedBy"          // asset → element（素材被哪个元素用）
  | "animatedBy"      // element → animation
  | "appliesTo"       // effect/mask → element
  | "appliesToScene"  // preset → scene（模板应用到场景）
  | "annotates"       // annotation/semantic-object → element
  | "contains"        // scene → track → element
  | "composes"        // preset → animationPreset

export interface GraphEdge {
  from: string;
  to: string;
  type: GraphEdgeType;
}

export interface ResourceGraph {
  nodes: GraphNode[];
  edges: GraphEdge[];
}
```

**关键接口**：

```ts

  rebuildFromDocument(doc: VideoDocument): ResourceGraph;   // 全量重建
  updateIncremental(doc: VideoDocument, change: DocumentChange): void;  // 增量
  // ★ 两个核心查询（AI 的高频问题）
  findRefs(objectId: string): GraphNode[];                  // "小明在哪出现过" → 关联元素/素材
  analyzeImpact(targetId: string): ImpactReport;            // "删素材 X 影响什么"
      // ImpactReport { directUses: {elementId, kind}[], cascade: {presets, annotations}[], suggestion: string }

```

**与 OpenCut v1 衔接**：
- **复用**：OpenCut 的 id 引用（mediaId/definitionId，§1.5/§1.6）是图的基础——元素已经引用资产，图只需把**已有的引用显式化成边**。
- **扩展**：OpenCut 无关系索引；本系统新增"preset→scene""annotation→element"等跨层边。
- **替换**：我们的 D1 债务（位置索引 type:ti:idx）**必须先在 Document 层改成 id 引用**（Phase 1），否则图无从建起。这是 Resource Graph 的硬前提。

### 3.6 AI Intent Layer（AI 意图层）

**为什么需要它**：高级 AI 操作不能是 `addEffect()`——那是命令，AI 直接发命令等于让 LLM 当"编辑器专家"，会错且不可复用。**AI 的产出必须是意图（语义级目标），翻译交给引擎**（背景要求第 6 条，Principle 4）。这条链：`AI Agent / Intent Layer / Planner / Command Generator` 四层，每层职责单一、可测试。

**决策（Intent 粒度）**：**AIIntent 是结构化的语义级目标对象**——粒度是"一个可验证的编辑目标"，既不是命令（太细）也不是自然语言（太糊）。示例粒度对比：

| 层级 | 示例 | 是否可作为 AI 契约 |
|---|---|---|
| 自由文本 | "让开头吸引人一点" | ❌ 无法程序化校验/执行 |
| **AIIntent** | `{type:"style-scene", sceneId:"s1", style:"hook-energy", params:{tempo:"fast"}}` | ✅ 结构化、可校验 |
| Command | `addEffect({elementId, effectId:"blur"})` | ⚠️ 太细，AI 不该懂 |

**数据模型**：

```ts
// ai-intent/intent.ts
export type IntentType =
  | "create-project"      // 新建项目（生成 Document）
  | "import-media"        // 导入素材
  | "apply-preset"        // 套模板 {presetId, target}
  | "edit-element"        // 编辑元素 {elementId, patch}
  | "arrange-timeline"    // 排列时间线（排序/剪裁/拼接）
  | "add-subtitles"       // 生成字幕（Whisper → 字幕元素）
  | "style-scene"         // 调风格 {sceneId, style, params}
  | "add-story-beat"      // 打故事节拍
  | "query"               // 只读查询（不修改，直接走 Resource Graph / Semantic）
  | "export"              // 导出

export interface AIIntent {
  id: string;                        // intent 实例 id（日志/回放用）
  type: IntentType;
  target?: IntentTarget;             // 作用对象
  params: Record<string, unknown>;   // 意图参数（Preset id、元素 id、风格、时间…）
  constraints?: {                    // 约束（Planner 必须满足）
    maintainUndoable: true;
    maxCommands?: number;
    requireAudit: true;
  };
  confidence?: number;               // AI 置信度（低置信度触发人工确认）
  source: "agent" | "mcp" | "skill" | "user-command";
```

- **替换**：我们的后端 Command API（90+）是 `CommandGenerator` 的现实宿主——Python 后端执行命令、前端薄壳，这条链完全保留（详见 §5）。

### 3.7 Collaboration / Event System（协作/事件系统）

**为什么需要它**：多人协作基础——A 改字幕、B 改颜色，互不冲突（背景要求第 7 条）。前提是：**所有变更都是 Command**（Principle 2），所以协作广播/冲突解决的原子单位天然是 Command。同时，AI 回放（undo/redo）、审计、远程预览，全部复用同一条**变更流**。

**决策**：**Operation Log = 我们现有 audit_log 的升级**；协作粒度 = **Command 级**（不是字段级，避免字段级 OT 的复杂度）；冲突解决 = **版本向量 + 命令级 merge**（简单可落地的方案，不做完整 OT/CRDT）。理由：视频编辑 90% 的冲突是"两个人改同一元素同一参数"，用命令级版本向量检测、让后提交者看到冲突并选择保留谁，比字段级 OT 简单一个数量级且足够用。

**数据模型**：

```ts

```

**与 OpenCut v1 衔接**：
- **复用**：OpenCut 的 `CommandManager`（execute/undo/redo 栈，§1.9）是 Operation Log 的**天然挂载点**——在 `command.execute()` 里加一行 `operationLog.record(cmd, args, source)` 即可，零侵入。`CommandResult.selection` 语义沿用（§1.9）。
- **扩展**：OpenCut 无任何协作/事件概念（单机架构）；新增 EventBus/OperationLog/ConflictResolver 三个横切组件。
- **替换**：我们的 audit_log 从"只记录"升级为"记录 + 重放 + 冲突检测"三合一。

---

### 3.8 Render Pipeline 深化（Render Graph）

**为什么需要它**：OpenCut 的渲染是 `Scene → Node Tree → Renderer` 单管线（§1.11），未来要有 LUT、AI 增强、超分、运动模糊——每个都是一层"像素变换"，没有明确的 Pass 结构就无法插入（背景要求第 8 条）。**Render Graph 把渲染从"节点树直出"升级为"固定 6-Pass 管线 + 可插拔 Pass"**。

**决策**：**Render Graph = Video → Mask Pass → Effect Pass → Color Pass → Composite Pass → Output 的固定骨架 + 插件可注册新 Pass**。骨架固定保证可预测，Pass 可插拔保证可扩展。LUT/AI 增强/超分/运动模糊全部实现为"注册一个 Pass"。

**数据模型**：

```ts
// render-graph/render-graph.ts
export type PassType =
  | "video"        // 解码 + 变换（transform/opacity/blendMode 解析，OpenCut resolve 阶段）
  | "mask"         // 蒙版（OpenCut masks：feather/invert/stroke）
  | "effect"       // 特效链（OpenCut effects 按顺序执行）
  | "color"        // 调色（LUT / 色彩分级 / 曝光 / 白平衡）
  | "ai-enhance"   // AI 增强（超分/去噪/补帧——future）
  | "composite"    // 合成（轨道层级、混合模式、透明度合成）
  | "output"       // 输出（编码 / 截图 / 送显示）

export interface RenderPassDefinition {
  id: string;                          // "lut.apply" | "super-resolution"
  type: PassType | "custom";           // 挂到哪一阶段；"custom" 需声明 after/before
  enabled: boolean;
  priority: number;                    // 同 Pass 类型内的顺序
  build: (ctx: PassContext) => RenderPassInstance;   // 插件提供
  paramsSchema?: JSONSchema;           // 参数描述（AI 可读）
}

export interface RenderPassInstance {
  run(input: FrameBuffer, params: unknown): FrameBuffer;  // 像素处理
  // 或声明式：{ shader?: {vertex, fragment}, params }
}

export interface RenderGraph {
  passes: RenderPassInstance[];        // 已按类型+优先级排好的管线
  frameInput: { node: RootNode; time: MediaTime };
  buildFromScene(scene: SceneDoc, doc: VideoDocument): RenderGraph;   // scene-builder 升级
}
```

**关键接口**：

```ts
export class RenderGraphManager {
  build(scene: SceneDoc, doc: VideoDocument): RenderGraph;   // 替代 buildScene
  addPass(def: RenderPassDefinition): void;                  // 插件注册 Pass
  render(graph: RenderGraph, time: MediaTime): Promise<FrameBuffer>;
  renderSinglePass(graph: RenderGraph, passId: string, time: MediaTime): FrameBuffer;
    // ★ 调试图/AI 看图用：单独跑某一 Pass
  export(graph: RenderGraph, opts: ExportOptions): Promise<Blob>;   // 复用 SceneExporter
}
```

**与 OpenCut v1 衔接**：
- **复用**：OpenCut 的 `buildScene`（§1.11）产生 RootNode 节点树——**作为 Video Pass 的输入保留**；`resolve`（transform/opacity/effects/masks 解析，§1.11）拆进 mask/effect 两 Pass；CanvasRenderer/GPU 双后端作为 pass 的**执行后端**。
- **扩展**：OpenCut 的 effect 是"元素级"；Render Graph 新增**帧级** Pass（color/ai-enhance/output），这是 OpenCut 没有的（OpenCut 只有元素级特效）。新增 color Pass 挂 LUT、output Pass 挂导出器。
- **替换**：`RenderTreeController` 重建 node tree 的逻辑改为"Document 变更 → RenderGraphManager.build() 重建 graph"（OpenCut 的 useDeepCompareEffect 触发点不变，只是重建产物从 node tree 变成 graph）。

**Step 3 —— Command Generator 实例化**：
- `CommandGenerator.realize(plan)` 把每条 plan command 映射到命令实现：
  - 我们后端已有 `project.create`/`media.import`/`timeline.insert`/`timeline.split`/`subtitles.generate` → **直接映射到现有后端 Command API**。
  - 新命令 `preset.apply`/`semantic.annotate`/`preset.apply-animation` → 由 Phase 1/2 新实现。
- 全部包成 **1 个 BatchCommand** → 执行。**一次 undo 撤销整个 AI 操作**（Principle 2 / 协作单位）。

**Step 4 —— EditorCore 执行**：

**Step 5 —— 结果验证**：
- 返回给 AI：`{executedCommands: 10, resultSnapshot, undoHandle}`。
- AI（或用户）可读取渲染结果截图确认效果；不满意则 `undoHandle` 一键回滚。
- 之后 AI 可追加新意图：如 `query`（"hook 段用了什么效果？"→ 走 Resource Graph/Semantic 查询），或 `style-scene`（"cta 段加个强调色"）。

## 6. 分阶段落地路径

> 原则：**Phase 1 必须小步快跑能落地**，每阶段有明确验收标准，不一口气全上。每阶段产出可独立交付、可被 AI 立刻使用的能力。

### Phase 1 —— 协议地基 + 命令全通（小步快跑）

**目标**：让 AI 能用一条命令生成一个带模板的工程文档。解决 D1（id 引用）+ 建立 Document Protocol + Plugin/Preset 骨架。

| 做 | 说明 |
|---|---|
| **Document Protocol v1** | 定义 `VideoDocument` schema + `DocumentManager`（create/load/save/validate/migrate）。先只做 `schemaVersion`/`metadata`/`assets`/`timeline` 四段，plugins/extensions/animation 留 schema 位。 |
| **D1 id 引用改造** | draft 段定位从 `type:ti:idx` 全部改为 `id`。这是最痛、收益最高的一项，且是后续一切的地基。 |
| **D3 时间整数化（渐进）** | 内部时间改 MediaTime tick，导出时换算成 float 给剪映。 |
| **Plugin v0（内置化）** | 建 PluginManager 骨架，把现有 effects/masks/graphics/subtitles 注册成"内置插件包"，对外暴露 `registerPlugin()` API。 |
| **Preset v0** | PresetManager + `applyPreset` 打通：先支持"style + timing"两段（animation 段留空），内置 2-3 个手工 Preset（小红书知识/口播/图文）。 |
| **后端命令补齐** | 新增 `project.create`（直出 Document）、`preset.apply` 两个命令；`timeline.split`/`insert` 等验证 id 引用后的正确性。 |

**依赖**：现有后端 Command API、C3 CommandService。
**验收标准**：
1. `POST /mcp/execute {cmd:"project.create", args:{presetId:"xiaohongshu-knowledge"}}` 返回一份合法 `VideoDocument`（JSON，schemaVersion=1，含 split 好的三段式轨道）。
2. 该 Document 可被编辑器加载、可 undo 一次整批撤销、audit_log 有完整命令链。
3. AI（LLM）能**读**这份 JSON 并回答"hook 段在几秒、用了什么模板"。
4. 自动化测试：位置索引引用造成的"找不到段" bug 清零（D1 验收）。

### Phase 2 —— 语义 + 图 + 事件（AI 变聪明）

**目标**：AI 能理解"角色/情绪/节奏"，能回答关系问题，协作基础就位。解决 D2/D4，建立 Semantic + Resource Graph + Event System。

| 做 | 说明 |
|---|---|
| **Semantic v1** | SemanticManager + SceneMeaning/StoryBeat/ObjectReference/IntentTag 落 Document；Whisper + LLM 自动标注入口（`semantic.generateAnnotations`）包成命令。 |
| **Resource Graph v1** | ResourceGraphManager：从 Document 全量重建 + 两个核心查询（findRefs / analyzeImpact）。语义标注进图。 |
| **D2 事件驱动** | 500ms 轮询 → EventBus 增量通知；audit_log 升级为 OperationLog（记录+重放）。 |
| **D4 动画模型升级** | 扁平 keys → bindings+channels（复用 OpenCut 模型）。这一步为 Preset 的 animation 段铺路。 |
| **Preset v1（含动画）** | Preset 增加 animation 段（引用动画预设），内置 Preset 扩展至 10+ 个；`applyPreset` 全链路（style+animation+timing）。 |
| **AI Intent v0** | IntentManager 骨架：`submitIntents` 接受结构化意图，apply-preset/import-media/create-project 三类先通，Planner 用规则（不是 LLM）生成计划。 |

**依赖**：Phase 1。
**验收标准**：
1. AI 提问 `query{question:"小明在哪出现过"}` 返回正确的元素/时间列表（Resource Graph + Semantic 打通）。
2. `applyPreset("xiaohongshu-hot")` 一次应用完整模板（含动画），undo 一次整批回滚。
3. 两个 client 同时改不同元素互不冲突；同元素冲突能被 ConflictResolver 检测并给出报告。
4. 500ms 轮询移除后，编辑器响应无感知差异（D2 验收）。

### Phase 3 —— AI 编排 + 渲染深化（完整平台）

**目标**：AI 一句话生成完整项目；渲染管线为未来 AI 视觉能力留好位置。解决 D5/D6，建立 AI Intent Layer 完整版 + Render Graph。

| 做 | 说明 |
|---|---|
| **AI Intent 完整版** | IntentLayer + Planner 接 LLM（自然语言→AIIntent），全部 IntentType 打通；Skill 编排（多步工作流：选题→素材→模板→字幕→导出）；staging 批量事务（Transient 层，失败全丢弃）。 |
| **Render Graph v1** | 渲染改 6-Pass 骨架：video/mask/effect/color/composite/output；LUT 作为第一个 color Pass 插件实现。**先保住现有渲染正确性**，Pass 化是内部重构。 |
| **D6 组件级复用** | 时间线/属性面板 DOM 增量渲染（订阅切片）。 |
| **D5 异步 ffmpeg** | 媒体导入异步化（后台线程探测/转码，不阻塞 UI）。 |
| **Exporter 插件化** | 剪映导出器 + MP4 导出器注册为 Exporter 插件；新增导出器=注册插件。 |
| **协作完整版** | 真实多人（版本向量 + 命令级 merge），OperationLog 重放/审计完整化。 |

**依赖**：Phase 1/2。
**验收标准**：
1. AI 一句话："做小红书知识视频，3 分钟学剪映，前 3 秒 hook" → 自动完成：建项目→套模板→导素材→排轨道→Whisper 字幕→套动画→导出剪映草稿，全程一条 undo 回滚。
2. 新增 LUT 特效 = 注册一个 color Pass 插件，5 行配置，不碰渲染骨架。
3. 多人在线编辑，冲突可检测可解决，审计日志可完整回放任何人的操作。
4. 导入大素材不再卡死 UI（D5 验收）；UI 跟手（D6 验收）。

| Plugin | 能力从内置变插件，可扩展 | manifest + 5 类注册 + PluginManager | P1 |
| Preset | 模板 = 风格+动画+节奏配方，非 keyframe 堆 | PresetDefinition{style,animation,timing,semantic} | P1→P2 |
| Semantic | AI 理解角色/情绪/节奏 | SceneMeaning/StoryBeat/ObjectReference/IntentTag | P2 |
| Resource Graph | AI 问"在哪出现/删了影响什么" | 派生图：usedBy/annotates/composes 边 | P2 |
| AI Intent | AI 表达意图，引擎翻译，不操作 UI | AIIntent → Planner → CommandGenerator | P2→P3 |
| Collaboration | 多人协作 + 审计重放 | Command 级 OperationLog + 版本向量 | P2→P3 |
| Render Graph | 未来 LUT/AI 增强/超分的插槽 | 固定 6-Pass + 可插拔 Pass | P3 |

## 附录 B：本蓝图最关键的 5 个决策（拒绝骑墙）

1. **Document Protocol 用 JSON**——AI 可读可生成可 diff；剪映导出已 JSON，兼容。
2. **引用一律全局唯一 id**——位置索引是 D1 债务的根，Phase 1 第一优先清除。
3. **Intent 是结构化语义目标**（非命令、非自由文本）——这是 LLM 与引擎之间可校验的契约。
4. **协作粒度 = Command**——撤销/审计/协作/AI 回放复用同一对象，不做字段级 OT。
5. **Render Graph 骨架固定 6-Pass**——可预测 + 可扩展，LUT/AI 增强只是新增 Pass。

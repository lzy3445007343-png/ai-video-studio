## 〇、背景：我们在做什么 / 要做到什么（GPT 读不了我们的代码和 OpenCut 源码，先交代清楚）

**一句话目标**：我们在从零自研一个**桌面 AI 剪辑软件**（类似剪映/PR 的界面，但核心是为"AI Agent 未来能通过指令操作剪辑"设计——所有用户操作都能被记录、回退、可被 AI 调用）。技术栈：Python + WebView2（本地桌面壳），前端原生 JS（无 React/Vue），时间轴/播放器/参数面板全部自研。

**当前阶段在做**：把「关键帧动画系统」做到**剪映/PR 专业级**（位置移动、缩放、旋转、透明度都可以打关键帧做动画）。这是"从参数面板改数值"到"真正的剪辑器"的分水岭。

**我们参考的对标**：开源项目 **OpenCut**（网页版剪辑器，TypeScript 写的，我们本地 clone 了它的源码做架构对照——但你可能读不到这份源码，所以本报告里所有 OpenCut 的行为结论都标注了来源：要么是用户实机截图证实，要么是我们读源码得出的，请区分对待）。

**本项目关键帧系统的核心设计**（已经做完并工作的部分）：
1. 每个素材（图片/视频）可以有多个"动画通道"（如 X 位置、Y 位置、缩放、旋转、透明度），每个通道上沿时间轴打多个关键帧（每个关键帧 = {时间, 值}），播放时在关键帧之间做插值 → 素材动起来。
2. **打关键帧有两条路径**（都对齐 OpenCut）：
   - **路径A｜参数面板 ◆ 按钮**：拖播放头到某时间点 → 在参数面板点 X 通道的 ◆ → 在该时间点打一个 X 关键帧（值=当前值）。
   - **路径B｜预览框拖素材**（本次问题核心）：拖播放头到某时间点 → 在预览画面里**用鼠标拖动素材**（素材跟着鼠标移动，X/Y 同时变）→ **松手瞬间自动生成一个 X+Y 双通道关键帧**（值=拖到的新位置）。——这条路径用户已用 OpenCut 实机截图证实：OpenCut 就是这样的行为。
3. **时间轴上的菱形**：每个关键帧在时间轴上显示为一个白色菱形，**同一个时间点如果 X 和 Y 都有关键帧，应该合并显示成一个菱形**（点它=同时选中 X+Y 两个关键帧；拖它=X+Y 一起动）。这是 OpenCut 的行为。
4. **选中多个菱形拖动**：Shift 点选多个菱形 → 拖其中任意一个 → **全部选中的一起移动，相对间隔保持**，松手一条 undo 整体回退。用户实测 OpenCut 这个操作完全正常。

**我们现在遇到的问题**：上面第 2 条路径B（拖预览素材自动打点）和第 3/4 条（菱形合并、组拖动），在我们自己软件里表现不正常——数据错位、像"复制"、参数值被改。具体见下文。

## 一、现象（用户操作 → 看到的）

### 操作链（用户实际做的）

| 步骤 | 操作 | 预期 | 实际 |
|---|---|---|---|
| 1 | 拖播放头到时间点 A → 参数面板点 X ◆ → 点 Y ◆ | 打 KF1（X/Y 同点） | ✅ KF1 同点（数据证实） |
| 2 | 拖播放头到时间点 B → **预览框拖素材**（X/Y 同时变）→ 松手 | 自动生成 KF2（X/Y 同点） | ❌ **X/Y 差 666660us（20帧整）** |
| 3 | 拖播放头到时间点 C → 预览框拖素材 → 松手 | 自动生成 KF3（X/Y 同点） | ❌ **X/Y 差 666660us（20帧整）** |
| 4 | Shift 选中时间轴上 KF2 + KF4（都变蓝）→ 拖其中一个 | 两个一起动，纯移动 | ❌ 见下方现象 2/3 |

### 现象清单

1. **时间轴菱形数量不对**：打了 3 个时间点（每点 X+Y 两个 KF），时间轴显示 **5 个独立菱形**（预期 3 个合并 marker）。因为 X/Y 时间戳错位，每点被拆成两个。
2. **"复制"感**：选中 2 个菱形拖动 → 原地留一个 + 拖出一个新的，像复制移动（OpenCut 里同样操作是纯移动，无此问题）。
3. **拖动后参数值被改**：从 KF2 拖到新位置，**X 轴的值变了**（数据里 X KF 的 v 从 -147.86 → 407.14，见下方数据），不是纯移动。
4. **素材库"全清空"**（B12）：拖动关键帧 / 拖动预览素材后，素材库卡片全部消失，反复出现（本报告不深入，另案）。
5. 之前：**拖菱形拖不动（弹回）**——已修（data-kid → data-kids 属性失配 + 缺 Refresh Lock），此项已解决。

## 二、真实数据（MCP 直读后端，铁证）

素材：`粗剪_IMG_4379_v2.mp4`，动画通道 `transform.positionX` / `transform.positionY`，各 3 个 KF：

| 时间点 | X 通道 (t, v) | Y 通道 (t, v) | X−Y 差 |
|---|---|---|---|
| KF1 | 1633333, 0.0 | 1633333, 0.0 | **0（同点 ✅）** |
| KF2 | 3783326, **-147.86** | 3116666, -115.71 | **666660us（=20帧整）❌** |
| KF3 | 5849993, **407.14** | 5183333, -117.85 | **666660us（=20帧整）❌** |

### 规律（关键）

- 两次错位都是 **666660us = 20 × 33333us**（33333us = 30fps 帧长，帧吸附单位）。
- 不是随机误差（随机误差不可能两次精确相等到微秒）。
- **强烈暗示：某处发生了"恰好 20 帧"的系统性时间偏移**——比如：打点/拖动过程中播放头被 seek 了 20 帧？或某次帧吸附把时间吸到了特定值？或两次 add_keyframe 用了不同的时间基准？

## 三、问题本质（我们的理解，可能不对）

用户"拖预览素材自动打 KF"的操作，X/Y 应该用**同一个时间基准**（preview-drag 一次 commit 里 X/Y 共用 `localSnap`，见代码），理论上**必然同点**。但数据却差整 20 帧 → 说明**打点链路某处引入了系统性时间偏差**，且偏差恰好等于 20 帧。这个偏差发生在"打点"还是"拖动"环节，目前未定论。

## 四、我们猜的层面（按可能性排序，待验证）

> 以下均为猜测，请独立验证。

1. **打点时间源（preview-drag localSnap）**：`pointerdown` 时快照 `localSnap`，`pointerup` commit 时用同一个值打 X/Y。理论上同点。若 X/Y 实际错位 20 帧，可能是：
   - 两次 add_keyframe 请求间播放头被别处 seek（如拖动中 renderAll 触发 seek）；
   - 或 `localSnap` 在拖动过程中被覆盖/重算。
2. **帧吸附的交互**：`snapFrame()` 按 30fps 吸附，若某处把时间吸附后再叠加，可能产生整帧偏移（20 帧恰是整数）。
3. **跨通道对齐逻辑（B3.4 加的）**：后端 `add_keyframe` 有"其他通道 ±1帧(33333us) 内有 KF → 对齐到该 KF 时间"。若 X 和 Y 打点时间本身差一点，对齐可能把 Y 吸到错误的 KF 上。但 20 帧远超 ±1帧 容差，这条可能不是主因。
4. **渲染合并容差**：timeline.js 按 ±1帧 合并同点多通道 marker。20 帧分离靠渲染层修不了——渲染只是"表现"，根因在数据。
5. **选中/拖动集合语义**：marker 合并后 `data-kids/data-paths` 逗号分隔；拖动时按选中集更新。若选择键或集合构造漏了某通道，会出现"只拖一个通道"→ 视觉上像复制。**用户数据里 X KF2 v 从 -147.86 → 407.14 被改，与 update_keyframe 传 value:null 相矛盾**（update_keyframe 不改值），所以**有别的写值路径**（可能 preview-drag 的 add_keyframe 合并更新了已有 KF 的 v）。

## 一、审计目标

回答一个问题：**"用户的一次操作，在事件流每一层到底怎么流转？哪些层重复触发/状态污染，导致了所有诡异 bug？"**

GPT 判断：KF 偏移 / marker 复制 / value 被改 / 素材库消失 / 拖动弹回，表面分属各模块，**实际可能同源——事件流某一层重复触发**。

```
用户操作 → Event → State 更新 → Render → Command → Backend
   ↓          ↓         ↓         ↓         ↓         ↓
pointer    handler   Store.set  renderAll  withTx    python API
           (DOM)     +订阅       +refresh   +undo     +落盘
```

## 三、审计方法（三步）

### 第 1 步：静态画图——事件触发链全图
对**每个入口**（拖时间轴段 / 拖 KF marker / 拖预览素材 / 面板输入 / 播放头拖动 / 素材库拖入 / 500ms 轮询），画一条完整链路：

```
[入口] → [事件] → [handler] → [Store.set 改了哪些 key] → [哪些订阅被触发]
        → [refresh/renderAll 跑了哪些] → [Command/事务] → [后端] → [响应回来又触发什么]
```

产出**状态流矩阵**（见 §五产物①），每条链路一行，标"是否有重复触发/环形触发"。

### 第 2 步：动态验证——链路日志（已有基础）
复用 8/22 已加的审计日志 + 补关键节点：
- `[KF-AUDIT]`（preview-drag pointerdown/commit、后端 received/stored）✅ 已有
- 补：`refresh()` 调用栈（谁触发的）+ `renderAll` 每次执行的时长
- 补：Store.set 的 key + 触发订阅者列表（一行日志）
- **验证 20 帧疑似链**：`pointerup → commit(KF) → refresh → get_state → renderAll → seek → 面板取新 playhead → 第二次 add_keyframe`

### 第 3 步：对照新版 OpenCut 的状态组织
新版是 `Editor Core + Managers`（media-manager / timeline-manager / selection 等）——单一数据源 + 显式 Manager 方法调用，**没有"refresh 全量重建"这种兜底**。
对比我们：Store + subscribeSlice 切片订阅 + 500ms 轮询 refresh——**轮询本身就是"全量重建"的源头**，是重复触发高发区。

| # | 疑点 | 现象 | 怀疑链路 | 验证方法 |

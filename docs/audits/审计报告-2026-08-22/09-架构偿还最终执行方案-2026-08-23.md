## 二、新增风险清单（08 完全未发现，R11-R20）

### R11 🔴 import_jianying_project 写「旧结构」草稿到盘，依赖隐式迁移（结构双重转换）

- **源码证据**：`main.py:4907-4909` 构造 `out = {"video": [], "audio": [], "text": [], "image": [], "sticker": [], "effect": [], "canvas": ...}`（**旧结构**）；`main.py:4971-4973` `self.state["draft"] = out; self.state["materials"] = new_materials; save_state(self.state)`。
- **问题**：整个系统其余部分全部写 X 结构（`overlay/main/audio`），只有此方法把旧结构直接落盘，靠下次 `load_state`（main.py:821-824）的 `_migrate_old_to_x` 静默迁移。后果：① 磁盘文件短暂处于旧结构，任何并发读取（桌面 500ms 轮询 / MCP）都要各自跑一遍迁移；② `_migrate_old_to_x` 是为「历史遗留草稿」设计的（依赖 `layer_order`、`video[0]` 当主轨），拿它处理导入的剪映工程是**语义错位**（剪映的 video[0] 不一定是主轨）；③ 迁移是运行时推导，导入结果与「真正 X 结构工程」的轨道语义可能不同。
- **发生条件**：每次 `import_jianying_project` 必触发。
- **隐藏保护**：无。`load_state` 的迁移只保证「不崩」，不保证语义。
- **修复**：M2 内一并处理——`import_jianying_project` 改为直接产出 X 结构（复用 `_ensure_track`/`_insert_track`），并包事务入 undo。

### R12 🔴 delete_material 引用检查在 X 结构下永不命中（比 02 P1 更严重）

- **源码证据**：`main.py:5131-5140` `for t in ("video", "audio", "text"): for segs in (draft.get(t) or []): for s in segs:`。
- **问题**：X 结构下 `draft["video"]`/`draft["text"]` 是 None；`draft["audio"]` 是「轨道 dict 列表」（`[{"segs":[...], "tid":...}]`），迭代 `draft["audio"]` 得轨道 dict，再 `for s in segs` 迭代 dict **键**（"segs"/"tid" 字符串），`isinstance(s, dict)` 恒 False → `referenced` 恒 False → **只要素材路径匹配就删文件**。02 P1 只指出「main/overlay 查不到」，红队实测 **audio 轨同样查不到**。
- **发生条件**：删除任意仍被时间轴引用的素材时触发。
- **修复**：遍历 `_iter_all_segs`（main.py:1108），按 `material_id` 优先匹配。

### R13 🔴 get_state 轮询路径内同步 ffprobe（读路径写盘 + 阻塞）

- **源码证据**：`main.py:4990-5012 get_state`（前端 500ms 轮询调它）→ `if _ensure_seg_src_full(self.draft): save_state(...)`；`main.py:1186-1206 _ensure_seg_src_full` → `duration_for(p, mtype)`（`main.py:1898 get_media_duration` 同步 ffprobe）。
- **问题**：读状态的方法里藏了「ffprobe 子进程 + 写盘」两种副作用。一旦存在缺 `src_full` 的段（旧草稿/剪映导入），每次轮询都会同步阻塞 ffprobe（最长 20~30s）冻结 UI；且 `get_state` 是**读路径**却会写盘（违反读路径无副作用原则）。
- **发生条件**：导入的旧草稿段缺 `src_full` 时，首次轮询必触发；此后回填落盘才不重算。
- **修复**：`_ensure_seg_src_full` 移出 `get_state` 热路径，改为迁移管线一次性回填（M3）；轮询内禁止任何写盘。

### R14 🔴 Api.last_committed 在 _reload 后不刷新 → undo 快照基线过期 → 撤销吞掉对方进程改动

- **源码证据**：`Api.last_committed` 只在 `Api.__init__`（main.py:2447）被赋值为 `deepcopy(self.draft)`；`_reload`（main.py:2449-2466）重读文件、替换 `self.draft`，**但不动 `last_committed`**；`save_state(record=True)`（main.py:1052-1055）用 `state["draft"] != Api.last_committed` 判断是否压快照，压的是**旧基线**。
- **问题（红队本次最重要发现）**：设桌面基线 F2，MCP 写入 F3。桌面下一次操作 `_reload()` 后 draft=F3，但 `last_committed` 仍是 F2。操作改 draft→F4，`save_state` 比较 F4≠F2 成立 → 压入快照 **F2**（不含 MCP 的 F3 改动）。用户按一次 Ctrl+Z → `undo()`（main.py:1004-1019）恢复 F2 → **MCP 的改动被一次撤销抹掉**，且没有任何提示。这不是「并发覆盖」，是「撤销主动回退到对方改动之前」——比 08 的 R1 描述更隐蔽、更日常。
- **发生条件**：任何「MCP/其他进程写入后，桌面进程做了新操作并撤销」的序列。
- **修复**：① `execute` 的快照改为在 `_reload` **之后**深拷贝当前 draft（`cmd.saved_state = deepcopy(self.draft)` 移到 reload 后）；② undo 恢复前用 `version` 乐观锁校验「磁盘 version 是否等于本命令执行时的 version」，不符则拒绝并提示冲突；③ M2 双轨收敛后 `last_committed` 语义并入 Command 的 saved_state，删除独立基线。

### R15 🟠 change_pitch 字段前端播放引擎未消费 → 预览音调恒随变 vs 导出保持原调

- **源码证据**：`audio-engine.js:146` `src.playbackRate.value = c.speed || 1`——Web Audio `AudioBufferSourceNode.playbackRate` **没有 preservePitch**，音调始终随变速；`set_segment_speed`（main.py:2761-2804）持久化 `change_pitch`；导出端 `_video_clip_settings`（main.py:1516-1542）读 change_pitch。
- **问题**：`change_pitch=False`（保持原调）时，导出剪映正确保调，前端预览却始终变调 → **预览≠导出的又一实例**。这是 04 报告「半实现字段」清单里的遗留，08 完全未提。
- **修复**：M5 双真源收敛时显式决策——要么声明「预览端不支持保调，change_pitch 仅导出语义」并在 UI 标注，要么前端用 Web Audio 保调方案（detune 反算，效果有限）。至少要把差异文档化，不能静默不一致。

### R16 🟠 Store.batch 异常路径：state 已改但订阅者从未收到通知

- **源码证据**：`store.js:90-101 batch`：`try { fn(); } catch (e) { this._batchDepth = 0; this._batchQueue = []; throw e; }`——`set()` 在 batch 内（store.js:104-108）已 `Object.assign(this.state, patch)`，但异常时 `_applySet` 从未执行 → 切片订阅者与 `_emit` 全都不通知。
- **问题**：UI 与 state 脱节（界面显示的旧值、state 是新值）；当前所有 batch 调用点都包了 try/catch（04 报告「隐性契约」），但契约未文档化、新调用点容易踩。
- **发生条件**：任何 `Store.batch(() => { ... throw ... })`。
- **修复**：batch 的 catch 分支补发一次 `_applySet(merged)`（已改的 patch 至少要通知），或 catch 后回滚已 apply 的变更。

### R17 🟠 import_jianying_project / transcribe_media 批量操作 undo 粒度粗（一次全回退）

- **源码证据**：`import_jianying_project`（main.py:4971-4973）整体替换 + 单次 `save_state` → 压一条快照，undo 一次全回退（覆盖用户现有工程无法部分回退）；`transcribe_media`（main.py:4457）`add_subtitles` 一次压一条。
- **问题**：AI 或用户误操作后无法部分回退；且 import 覆盖现有工程**没有 undo 入口**（08 的 R5 只提了「无回滚」，未提 undo 粒度）。
- **修复**：import 包事务入 undo（回滚到导入前）；transcribe 每批字幕段合并为一条事务命令。

### R18 🟠 特效 keyframes 第二套 schema，导出端完全不处理（preview 有动画、导出无动画）

- **源码证据**：`effects.js:42-72 effectParamAt` 按 `[{param,time,value,easing}]` 插值（预览有效果动画）；`main.py:4236-4237 add_effect` 存 keyframes；导出端 `_apply_keyframes_to_segment`（main.py:1653）只处理段通道 `animations`，**特效 keyframes 无导出映射**。
- **问题**：特效参数动画「预览有、导出无」——导出剪映后参数是静态的。08 M5 任务 3 提了「并入统一 channel 或显式声明」，红队确认此处理正确但要求强调：这是**正确性问题**（预览≠导出），不是「模型统一」的洁癖问题，M5 必须给出明确处置（首选显式声明 + 导出降级映射）。
- **发生条件**：带 keyframes 的特效段导出时必触发。

### R19 🟠 _track_meta 与轨道数组 index 对齐脆弱，前端独立重算一遍

- **源码证据**：`main.py:521-547 _ensure_track_meta/_meta_of`（按 overlay index 对齐）；`main.py:585-636 _collapse_empty_tracks`（同步压缩两数组）；`timeline.js:159-173 trackMeta`（前端重新映射）。
- **问题**：任何绕过对齐函数直接改 overlay/audio 数组的路径（如 R11 的旧结构写盘、R17 的整轨替换）都会让 meta 错位（muted/hidden 挂到别的轨）。08 未单独处理。
- **修复**：M1 一并把 `_track_meta` 并入轨道的不可变更新路径——轨道对象内置 meta 字段（`track.meta`），淘汰平行数组。

### R20 🟡 previewState.visualEls 悬挂引用无清理（段删除后 wrap 残留）

- **源码证据**：`renderer.js:142-143` 复用元素但段删除后无回收；`preview-drag.js:78-83` 注释自认「wrap 残留于 previewState，无清理路径」。
- **发生条件**：反复增删段，`visualEls` 累积死条目（隐藏 DOM + 引用）。
- **修复**：M4 渲染改造时加「当前 draft 可见 key」GC（对 previewState 三张 map 统一清理）。

## 四、V2.5 必要能力补充检查（08 缺什么 / 为什么需要 / 放哪个里程碑）

> 对照 V2 圣经 §3 的五个横切能力维度，逐项核对 08。

### 4.1 Document：schema / migration / validation

- **08 有**：M3 schemaVersion + 迁移器（`_ensure_*` 收敛）；M6 `doc-protocol/schema.py` + loadDocument/saveDocument。
- **08 缺**：**validation 语义未定义**——`loadDocument(raw)` 对「缺字段」（补默认值）vs「非法值」（明确报错）没有分层；`_migrate_old_to_x`（main.py:724）与 `load_state`（main.py:830-873）当前是「静默 setdefault + 补默认值」，会把任何脏结构「救活」，掩盖真实错误。
- **为什么需要**：AI 生成 Document 是 V2.5 验收主场景，AI 输出必然有 schema 偏差。没有分层校验，「AI 生成的坏文档」会被静默修复成「能打开但语义错」的草稿。
- **放哪个里程碑**：M6（Document Protocol v1）必须包含 `validateDocument(raw) → {errors, warnings, repaired}` 三态结果；M3 只做「字段补齐」，非法结构（类型错/引用悬空）必须返回错误而非静默。

### 4.2 Command：args / replay / transaction / operation log

- **08 有**：M2 加 args + 单轨入栈 + audit_log 带 args；事务（已有 begin/commit/abort，M2 三修）。
- **08 缺**：① **redo 的 args 重放定位错误**（见 0.2-1，红队已改）；② **operation log 不落盘**——08 明确不做 undo 持久化（「不做清单」第 8 条），红队确认此决策正确（undo 栈落盘依赖命令可重放，OperationLog 是 P2 的事），但 M2 的 audit_log 至少应**可选落盘**（append-only JSONL，供 AI 审计重启不丢），否则「谁改了什么」的护城河仍只在单进程存活期内成立（05 D-103）。
- **为什么需要**：AI 批量操作后进程重启，audit 丢失 = 无法追溯/无法回滚建议。
- **放哪个里程碑**：M2 收尾加 `audit_log.jsonl` 追加写（不改变 undo 语义，仅审计持久化）。

### 4.3 Event：change event / version / subscription

- **08 有**：M4 事件 + version 门控 + slice 切换。
- **08 缺**：**change payload**（见 0.2-3）——事件只有 version 没有「谁变了」。没有 payload，M4 的「切片差量渲染」只能靠前端 diff 前后 draft 引用，代价回到全量比较。
- **为什么需要**：事件系统的价值就是「增量通知」；没有载荷的推送只是「轮询的推送版」。
- **放哪个里程碑**：M4。事件定义 `document-changed {version, changedSegIds[], changedKeys[], changedMaterials[], actor}`。

### 4.4 Plugin：registry / lifecycle / manifest

- **08 有**：M6 `plugin/plugin.py` PluginManifest + PluginManager.register/load/query + effects 注册表收敛 + 前端 css 适配器自动生成。
- **08 缺**：**lifecycle 定义**——`loadPlugin` 的依赖解析、`unloadPlugin` 的反注册顺序、启停状态机。08 的 Plugin v0 只做「注册表收敛」。
- **为什么需要**：V2.5 阶段内置插件包（effects/masks/subtitles）没有真实 load/unload 需求，lifecycle 可以简化；但 manifest 必须预留 `dependencies` 字段位（剪映导出器/字幕插件会用到）。
- **放哪个里程碑**：M6。v0 只做 register/query + 内置包，lifecycle 简化为一句话注释声明「v1 再实现依赖解析」。

### 4.5 AI Agent：intent / plan / execution / rollback

- **08 有**：M6 Intent v0（validate/decompose/规则 Planner/submit_intents/事务包批）。
- **08 缺**：① **Intent 校验 schema 未定义**（`submit_intents` 收到非结构化输入如何拒绝）；② **plan 的记录与重放**（`CommandPlan` 不落盘，AI 无法复盘「这次到底执行了什么」）；③ **staging（Transient 层）语义未明确**——V2 Principle 3 要求 AI 批量先写 Transient staging，失败全丢弃；当前只有后端事务（begin/commit/abort），没有「前端/意图层 staging」。
- **为什么需要**：staging 是「AI 批量不污染 Document 与撤销栈」的前提；不落盘 plan 则无法审计 AI 决策。
- **放哪个里程碑**：M7。staging 复用后端事务即可（begin 前快照 = staging 的折叠版本），但要显式声明「Intent 失败 → abort_transaction 整体回滚」为唯一路径；plan 记录进 audit_log.jsonl（M2 产物）的 meta。

## 五、4 个争议点的最终裁决

### 争议点 1：M1/M2 顺序（id 化 vs Command 闭环）—— **裁决：维持 08（M1 先于 M2）**

- **理由**：① M2 的 Command 要记录 args，若 args 仍用 `(type,ti,idx)` 位置引用，则「操作日志」记录的是**漂移引用**——redo/审计/OperationLog 全部建在流沙上；M1 让 args 先以 `seg_id` 为准，M2 记录的才是稳定快照。② 波纹引擎（main.py:1747 compute_ripple_adjustments）本就依赖段 id 配对 before/after，M1 的 `_ensure_seg_ids` 收敛到段工厂（D1-03）是 M2 之前就该有的地基。③ M1 是「参数层」改动（加 seg_id 首选、位置参数保留兼容），M2 是「命令层」改动（args 记录 + 入栈语义）——两者确有先后依赖（命令参数的可确定性依赖 id 引用），GPT 认可的前提成立。
- **边界收紧**：M1 只做「引用参数化」，不得碰 undo/redo 语义；M2 只做「命令记录」，不得新增引用字段。两阶段在 `delete_material`（R2/R12，M1）与 `_abort_tx` diff（M2）处交接。

### 争议点 2：Event 同步排位（08 放 M4 vs GPT 建议提前）—— **裁决：调整——事件推送本体维持 M4，但 version 语义 + 轮询门控提前到 M2**

- **理由（为什么不全盘提前）**：当前系统的数据一致性核心问题是「谁是真实状态」——这个答案现在是文件 + 内存双轨，靠乐观锁（M2）解决；「什么时候变化」靠 version（M2）；「谁知道变化」靠推送（M4）。前两个（M2）解决的是**正确性**，第三个（M4）解决的是**时效与性能**。事件推送牵动全部前端渲染（refresh/renderAll/slice 三处大改），在 M1/M2 未稳定时动它回归面失控。GPT「最大的问题不是性能而是数据一致性」的判断，红队认同**一半**：数据一致性缺陷的真实根因是 R1/R5/R14（写路径正确性），不是轮询本身；轮询只是「感知滞后」。
- **调整动作**：① M2 引入的 `version` 字段同时承担「乐观锁比较值」与「前端轮询门控值」双职责——`get_state(since_version)` 无变化返回空，前端只在 version 变化时走全量拉取（08 原计划放 M4 的第 2 步提前到 M2）；② M4 专注事件推送（mcp_state 变更通道 + document-changed 带 payload）+ slice 切换 + keyed diff + RefreshGate。
- **验证**：M2 完成后把轮询间隔从 500ms 调到 2000ms，功能零变化（因为门控保证只有真实变化才拉全量）。

### 争议点 3：schemaVersion 排位（08 放 M3 vs GPT 建议 M1）—— **裁决：调整——M1 收尾写入 schemaVersion 字段，M3 建完整迁移管线**

- **理由**：GPT 的核心担忧是「M1/M2 就改数据结构，没有版本迁移很危险」。红队核实：M1（id 化）与 M2（args 记录）**不改变文件结构**——id 化是加参数不是改格式；args 是内存对象字段，不落盘。严格说 M1/M2 不需要 schemaVersion。但：① M1 大规模改动所有写路径，任何一处漏改都可能让文件结构漂移，有版本字段才能第一时间检出「写出的文件是什么格式」；② 成本约 10 行（`schemaVersion: 1` + load_state 读取检查 + 日志），风险几乎为零；③ 与 08 M3 的迁移器管线不冲突——M1 只立字段，M3 才建「版本驱动迁移器」。
- **调整动作**：M1 任务清单末尾加一项「draft_state.json 顶层写入 schemaVersion=1；load_state 检查：缺字段/低于当前 → 打印 `[SCHEMA] legacy file, will migrate`（暂不迁移，仅标记）；`_ensure_*` 系列维持现状」；M3 正式把 `_ensure_*` 收敛进迁移器并支持 v1→v2 级联。
- **验证**：M1 完成后用旧文件（无 schemaVersion）启动，日志出现 `[SCHEMA]` 标记且功能零变化；M3 完成后旧文件自动升级到 v1 并打印 `[MIGRATE] from=0 to=1`。

### 争议点 4：Intent 拆分（08 全放 M6 vs GPT 建议 M6=Document/Plugin/Preset、M7=Intent）—— **裁决：采纳 GPT 拆分**

- **理由**：① 方向确实不同——Document/Plugin/Preset 是「地基能力」（AI 可生成文档、能力可扩展、模板可复用），Intent 是「AI 控制层」（消费地基）；捆绑会让 M6 同时承担「协议改造 + 注册表收敛 + 模板 + 意图编排」四项互不隶属的大改，无法独立验收。② Intent v0 的验收（submit_intents 一次整批回滚）依赖 M2 命令链、M6 的 preset.apply、以及 D5 的 transcribe_media 异步化（add-subtitles intent 的宿主）——D5 放 M7 使 Intent 验收完整。③ 08 自己把「时间统一收口」「D5 异步化」塞进 M6，这三件事与 Document/Plugin/Preset 无依赖关系，塞一起只会让 M6 变成「什么都做一点」。
- **调整动作**：M6 = Document Protocol v1 + Plugin v0 + Preset v0（验收：AI 生成 Document 可加载、新增特效只改 effects.json、preset.apply 可一键排版）；M7 = Intent v0（submit_intents 规则版）+ D5 最小任务队列 + 时间统一收口（验收：一句话批量操作一次 undo、长任务不卡 MCP、无散落换算）。

### 8.3 不应该做（防止团队踩坑）

| 事项 | 为什么不做 |
|---|---|
| **重写 main.py** | 90+ 命令/MCP/事务/草稿层已到 V1 功能等价，AI 通道超越（06 #20）；重写 = 丢全部测试资产 |
| **引入前端框架（React/Vue）** | 27 个 vanilla JS 模块 + HTML 内联主脚本；D6 目标用原生 keyed DOM 即可达成 |

| **接 LLM 做 Planner** | 规则 Planner 可测试可审计；LLM 解析放 MCP/Agent 侧，引擎保持确定性 |
| **做真多人协作/CRDT/OT** | V2 已选「命令级 OperationLog + 版本向量」够用；前提是命令自包含化（V3） |
| **做完整 Resource Graph/Semantic** | 图是派生数据，依赖 id 引用（M1）+ Semantic 挂载点（V3）；现在建 = 建在漂移引用上 |
| **MP4 渲染导出** | 业务定位是剪映草稿导出；MP4 是新产品不是债务 |
| **undo 栈持久化跨重启** | 依赖命令可重放；V2.5 只做 audit 落盘 |
| **给位置引用全面补丁（继续修 ti/idx 语义）** | `_overlay_index` ti 计数起点已不一致（D1-02）；正确动作是 M1 直接 id 化 |
| **do `import_jianying_project` 整轨替换**（在不修 R11 的前提下继续用） | 旧结构写盘 + 隐式迁移 + 无 undo = 三重隐患；必须 M2 一并修 |
| **前端预览保调实现（change_pitch）** | Web Audio BufferSource 无 preservePitch，保调实现复杂且收益低；正确动作是显式声明差异（M5-R15） |

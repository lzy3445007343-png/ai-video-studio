## 一、总览

该项目经历了大量"当时能跑、现在成为负担"的增量补丁，整体呈现出明显的**补丁叠加特征**：

1. **同一问题被多次打补丁**（如 src_end 推导在 main.py 至少 5 处重写、trim 公式 v1/v2/v3）；
2. **迁移期双轨并存**（legacy/slice、legacy/viewport、params/旧字段 mirror），且有 feature flag 恒为旧值；
3. **诊断打点留在生产路径**（KF_AUDIT 默认开、`[renderAll start]` 每 500ms 打印、debug=True 开发者工具）；
4. **死代码/占位代码保留**（`_push_undo` 空实现、audio-engine `setAnchor` 旧锚定、`renderSliceMode:"legacy"` 双跑）。

下表共 **22 条** 具代表性补丁债务。详细说明见第二节。

## 三、补丁详情说明（按债务影响排序）

### 3.1 双真源数据模型（P-022，最重债务）

**位置**：`property/property-kernel.js:29-57`（LEGACY_READ / LEGACY_MIRROR / LEGACY_CHANNEL）；`property/preview-coordinate.js:7-77`；`renderer.js:698-736`（resolveTransform 三层解析）。

**解决的问题**：把 `seg.transform.x`/`seg.volume` 等旧字段平滑迁到 `seg.params["transform.positionX"]`/`seg.params["audio.volume"]` 新模型，迁移期保证后端/导出读旧字段正常。

**现在的负担**：
- `setProperty()`（property-kernel.js:71-76）每次写 `params` **并同时写旧字段**（LEGACY_MIRROR）；`getProperty()`（:62-68）读取顺序是 `params → legacy → default`。**任何绕过 kernel 直接写旧字段的代码（如后端 update_segment_transform 只写 `seg["transform"]`）都会让 params 成为 stale 真源**，读侧永远拿到旧 params 值。
- preview-drag.js:116-134 静态 transform 提交路径：先 `setProperties(seg, params…)` 再 `update_segment_transform`，后端落盘只存 `seg.transform`，**params 在下次 refresh 后丢失**——双真源在"写侧 A、读侧 B"之间反复横跳，是全项目最隐蔽的一致性隐患。
- preview-coordinate `mode` 默认 "legacy"，但 HTML initZoomControls 硬切 "viewport"，两套换算并存。

**建议**：Strangler 收尾——params 为唯一真源，LEGACY_* 表只读（迁移读取），全部写入收口到 setProperty；后端 update_segment_transform 也改为写 `seg.params`。

### 3.2 每次写盘全量 IO + 全量快照（P-002 / P-003 / R-504）

**位置**：`main.py:1040-1091` save_state；`main.py:917-1032` CommandManager。

**解决的问题**：跨进程抢写导致假成功/段丢失（历史事故多次）；撤销栈从裸快照升级为 Command 栈。

**现在的负担**：
- 一次普通命令 = `_reload`（读盘+JSON parse）+ `execute` 里 deepcopy(saved_state) + `save_state` 里 push_snapshot deepcopy + last_committed deepcopy + 写盘 + **读回整树深比较**。
- CommandManager 有 cap=100，undo 栈最多 100 × 全草稿深拷贝常驻内存。
- 500ms 轮询 + MCP 高频写叠加，IO 放大系数约 3~4 倍。

**建议**：快照改"操作路径级"（只存被改段），或至少把读回验证改成抽样；undo 栈压缩（相同段快照去重）。

### 3.3 三层 Refresh Lock 无看门狗（P-018）

**位置**：`工作台v0.8时间轴.html:3218-3235` refresh()；`property/kf-panel.js:45-46`（`_kfEditing`）；HTML `:2135-2223` startKfMarkerDrag（`_kfDragActive`）；`property/interaction-kernel.js:69-72`。

**解决的问题**：500ms 轮询在交互/输入期间覆盖本地临时态（拖不动、参数被改、点击被吞）。

**现在的负担**：三层锁由**三个独立来源**置位/复位，`startKfMarkerDrag` 的 up 回调里 `_kfDragActive = false` 在逻辑中途（HTML:2199）置位，若之前 `move`/`up` 抛异常（如 `segEl.querySelector` 返回 null 后 `.style` 访问），锁永不释放 → refresh 永久跳过 → **UI 冻结但无任何提示**。

**建议**：RefreshGate 引用计数 + `setTimeout` 看门狗强制解锁；kf 拖拽整体包 try/finally。

### 3.4 诊断打点留在生产路径（P-004 / P-009 / P-014 / P-017）

`KF_AUDIT`（main.py:2964）默认开、`renderAll` 每 500ms 打点、`webview.start(debug=True)`、save_state 失败 traceback——全部是排查事故时的临时观测手段，事故结束后未回退。它们让生产代码每 0.5 秒执行一次不必要的 I/O 和日志，并在 `debug=True` 下把 WebView2 调试端口暴露给本地页面。

### 3.5 迁移对照期的双跑代码（P-016 / P-021 / P-022）

`renderSliceMode:"legacy"`、audio-engine 旧锚定、preview-coordinate legacy 模式，三处"对照期"代码全部保留，注释里都写着"验证后切/删"，但没有一处完成了收尾。这符合 Strangler 模式的预期中间态，但**没有任何切换时间表或 owner**，长期双跑既是性能损耗也是回归面。

## 四、同一问题的补丁演进链（"补丁的补丁"实锤）

这些是同一根因被反复打补丁的典型，最能说明补丁债的复利效应：

### 4.1 src_end 源终点推导演进链（至少 6 处独立实现/重写）
- **v1**：`main.py:3484-3486`（_trim_core）"src_end 缺失时实时 ffprobe 探测"——慢 + 阻塞。
- **v2**：`main.py:3494-3497`（_trim_core）"双向公式改反算，杜绝 (se-ss)/speed 失同步"——用户实测 dur=36.69s 但 se=6.19s 后修复。
- **v3**：`main.py:3512-3530`（_trim_core right）"①上限用 src_full ②反算 ③se 上限 clamp"——拉长恢复被裁帧 + 越界脏数据。
- **同构实现**：`playback-graph.js:48-50` `deriveSrcEndUs`、`player.js:427-428`（drift 内联）、`main.py:4663-4666`（导出）、`main.py:4704-4707`（导出音频）、`timeline.js:417`（波形）、`renderer.js:703-712`（resolveTransform）——**同一个公式在 6+ 个文件重复实现**，一旦语义变化（如引入变速+裁剪联动）需要同步 6 处。

### 4.2 素材"放不进/消失"根因修补链（至少 4 层）
1. `main.py:1052-1091` save_state 加读回验证（防假成功）；
2. `main.py:2536-2543` add_to_timeline 整体 try/except（静默失败 → 可见错误）；
3. `main.py:2548-2551` 进轨前 path 存在性校验（AI 传假路径）；
4. `main.py:2609-2622` material 归一匹配 + seg.path 改写 canonical（时间戳后缀 miss）。

每层都是对上一层"漏网"的修补，最终形成 4 层防御，但**任意一层的防御逻辑本身出错（如路径改写方向写反）都需要读者逐层理解**。

### 4.3 播放首播/跨段无声修补链（player.js / media.js 内 15+ 处日期注释）
`MEDIA_ACTIVATION_TIMEOUT`（player.js:98）、`_seekConfirmKeys`（:144）、`_waitSeekSettled`（:183-224）、`_waitMediaReady`（:230-248）、`_tryReloadMedia`（:253-306）、`_silentPrimeUrl`（:332-345）、drift 静默期（:423）、playTick 2500ms 重试（:611-617）、`_handleCrossSegment` 锁（:577-600）、`_lastPlayAll` 250ms 防抖（media.js:70）——**同一目标（"首播必须响"）被 10 个防御补丁层层包围**。每新增一个补丁都伴随"上一次补丁失败"的注释，但没有任何一份文档汇总这些补丁的触发条件与协作顺序，新成员（或 AI）改任一处都可能拆掉另一处的假设。

## 五、补丁注释分布（Grep 量化）

## 六、未被纳入但值得知晓的次生债务

1. **`mcp_server.py:349`** heartbeat 线程每 3s 写 mcp_state.json + 桌面每 500ms 读它：跨进程状态文件高频 IO（可合并为进程内内存状态 + 事件通知）。
2. **`工作台v0.8时间轴.html:2761`** importJyBtn 默认路径硬编码 `"E:\草稿\JianyingPro Drafts\5月2日\..."`——个人路径泄露进产品代码。
3. **`start.bat:6`** 用 powershell 杀所有命令行含 `main.py` 的 python 进程：粗粒度进程清理，可能误杀用户其他同名脚本（文档注明 allow_reuse_port 才是正解）。
4. **`renderer.js:147-165`** renderPreview 中 `media.oncanplay = onReady` 用**单归属属性**而非 addEventListener（注释说明刻意如此），但同一 wrap 多次切源会覆盖旧回调——与 player.js `_waitMediaReady` 的 addEventListener 风格不一致，属历史遗留写法。
5. **`store.js:94`** batch() 内 set 立即改 state 但延迟通知：若 batch 中 fn 抛异常（catch 后 rethrow），**state 已部分生效而订阅者从未收到通知** → UI 与 state 脱节。当前所有 batch 调用点都包了 try/catch，属"隐性契约"。
6. **`audio-engine.js:146`** `src.playbackRate.value = c.speed` 未处理 `change_pitch`：变速时音调始终随变（`src.playbackRate` 无 preservePitch），与 set_segment_speed 的 `change_pitch` 语义（False=保持原调）不一致——后端字段有、前端引擎没消费，属**半实现字段**。

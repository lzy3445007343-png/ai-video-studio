# 08 · 架构偿还施工图（可执行重构规划）

> 文档性质：架构偿还路线（Debt Paydown Blueprint）。不是重新审计 bug，而是回答"**按什么顺序、动哪些文件、做到什么程度，把当前系统还到 V2.5 架构稳定版**"。
> 输入：V1 架构圣经（opencut-架构圣经-v1）· V2 架构圣经（ai-native-架构圣经-v2）· 审计报告 01-07（同目录，2026-08-22）
> 验证：抽查 main.py（5219 行）/ mcp_server.py（361 行）/ store.js / 工作台 HTML，所有行号均已核对源码事实。
> 执行纪律：**做完一个接着做下一个**，不绑时间；每个里程碑独立可交付、可验证、不依赖后续阶段才能用。
> 最终目标：**V2.5 架构稳定版** = ① id 化 ② command 闭环 ③ event 同步 ④ 数据版本控制 ⑤ 删除历史补丁 五件事全部完成 + Document 协议种子（schemaVersion）+ Plugin/Preset 骨架。AI agent 自动剪辑、多 agent 协作、skill 市场、插件生态是地基完成后（V3+）的事。

## 一、当前架构健康度评分

**总分：32 / 100**（"能跑、AI 能调，但每改一处都要过五关斩六将"的补丁型架构）

| 维度 | 分数 | 一句话依据 | 关键证据 |
|---|---|---|---|
| 数据模型 | 20 | 无 Document、无 schema、无版本迁移；位置索引为主、双真源并存、5+ 对象有 3 份物理拷贝 | 02 报告 §3 单一事实来源矩阵；`draft_state.json` 的 `version` 是时间戳非版本号（main.py:1062） |
| 命令系统 | 40 | 有统一 `execute` + 审计 meta，但命令不记 args、双轨入栈、undo 整轨快照无重放能力 | `Command.__slots__` 无 args（main.py:892）；`push_snapshot`/`execute` 双轨（main.py:917/927）；06 报告 #2 |
| 同步机制 | 15 | 500ms 轮询 + 全量 `renderAll` + 4 个冻结锁；跨进程读-改-写无乐观锁 | HTML:3362 轮询；store.js:77 `renderSliceMode:"legacy"`；05 报告 A-101 |
| 时间系统 | 30 | µs/ms/s 三套并存，帧吸附前后端各一套实现（33333 硬编码 vs `Math.round(1e6/30)`） | main.py:1416 `_frame_snap_us`；edit-context.js:24；03 报告 D3-01 |
| 渲染 | 35 | 前端 DOM 合成 + Python 导出两套实现靠对拍脚本守护；时间轴每 0.5s 全量销毁重建 | renderer.js:110 vs main.py:4543；timeline.js:491-603；06 报告 #13 |
| 可扩展性 | 30 | effects.json 单一真源是唯一亮点；无插件 API、无协议、注册表散落、css 适配器需人工镜像 | effects.json:2 注释自述；06 报告 ② Plugin 25% |
| AI 可控性 | 60 | **全场最强资产**：90+ 命令统一入口 + MCP 30+ tools + 审计 meta（actor/reason/confidence/source） | main.py:2477 `Api.execute`；mcp_server.py；06 报告 #20 "超越" |

评分逻辑：AI 可控性靠"命令宿主完备"拉到全场最高，但其余六项都被"单文件 + 位置索引 + 轮询"这一底座拖住——**所有低分项同根**：没有协议就没有数据模型，没有事件就没有同步，没有 id 就没有引用安全。这就是为什么偿还路线必须以"解三件事的咬死"（数据源 / 定位 / 同步）为第一优先级。

## 二、最大 10 个结构性风险（按严重程度排序）

> 证据引用格式：`报告号-条目`（如 `05 A-101`）+ 源码 `文件:行号`。所有风险均为**结构性**（修一个 bug 不解决，要改架构）而非单个 bug。

### R1 🔴 跨进程读-改-写竞态：桌面 vs MCP 静默丢失编辑
- **风险描述**：桌面窗口与 MCP 是独立 OS 进程，共用 `draft_state.json`。各自 `load_state()` → 内存改 → `save_state()`。文件锁（main.py:1063-1066，portalocker）只保护写盘瞬间，**不保护"读-改-写"整体**：A reload 后 B 也 reload（同一基线）→ A 写 → B 写覆盖 A。无冲突检测、无提示。
- **证据**：`05 A-101`（read-modify-write 竞态）；`05 A-102`（事务超时 abort 清掉对方改动）；`05 C-107`（redo 基于过期基线）；`02 P11`（undo 跨进程不同步）；`main.py:908` 注释"共用同一份历史"不成立——类级属性只在单进程内共享。
- **不修的后果**：用户"刚调的音量没了"、AI 批量操作与用户操作互相覆盖，**当前已存在**，且随 AI 使用频率线性放大。这是数据安全级问题。
- **修的风险**：引入乐观锁/CAS 后，`save_state` 返回语义变化，所有调用点（20+ 处忽略返回值的）都要过一遍；若改成"单一写者（MCP 转发桌面）"则 MCP 链路延迟增加。改动面集中在后端，前端无感。

### R2 🔴 `delete_material` 误删仍被引用的素材文件
- **风险描述**：`delete_material`（main.py:5114-5153）的引用检查遍历 `draft["video"]/["audio"]/["text"]`——这是**旧结构**；当前结构是 `draft["main"]/["overlay"]/["audio"]`（main.py:791-799）。main/overlay 里的段永远查不到 → 时间轴仍引用的素材被当"无人引用"删文件。
- **证据**：`02 P1`（🔴 最高优先）；`02 报告 §3` 单一事实来源矩阵 Asset 行。
- **不修的后果**：删素材 → 导出剪映 `VideoSegment(None)` 抛异常、预览黑屏。**文件丢失不可逆**。
- **修的风险**：极低。只需把遍历改为 `_iter_all_segs`（main.py:1108 已存在现成函数）。这是全清单里性价比最高的一修。

### R3 🔴 Command 不记 args + 双轨历史：undo 漂移、无法重放
- **风险描述**：`Command.__slots__` 只有 `cmd_id/label/meta/saved_state/post_state/changed_paths/count`（main.py:892），**无 args** → redo 只能恢复 post_state 快照，无法重放命令。同时 5a 兜底 `push_snapshot`（main.py:917）与 5b `execute`（main.py:927）双轨并存：`save_state(record=True)` 每次真实变更压 snapshot，execute 靠"弹掉多余 snapshot"（main.py:948-949）掩盖——只弹 1 条，多个方法内部调 2 次 save_state 就残留多余快照（`toggle_source_audio`/`add_bookmark`/`toggle_bookmark`）。
- **证据**：`01 报告 §5.3` P3-1（多快照残留）；`07 P0-2`；`04 P-002`（execute 只弹 1 条快照）；`06 #2`（"无法重放命令"是 v2 OperationLog 的硬伤）；`main.py:1034` audit_log 无 args 字段。
- **不修的后果**：undo 一次只回一半；AI 无法审计"当时参数是什么"；OperationLog 重放、协作广播、AI 回放全部无从谈起——**直接封死 V2 的 ⑦ Collaboration 系统**。
- **修的风险**：`Command` 加 args 字段 + `save_state` 双轨收敛，改动集中在 CommandManager 与 `save_state`（后端一个文件）；前端 `CommandService` 无感。风险中低，但要求一次做完避免中间态。

### R4 🔴 位置索引引用：关键帧/遮罩/特效/AI 命中错段
- **风险描述**：段有稳定 `id`（draft_state.json:24），但 `add_keyframe`（main.py:2936）/`set_mask`（main.py:3691）/`update_effect`（main.py:4282）/`set_track_meta`（main.py:4465）签名**均无 `segid`**，前端 `kfSegArgs()` 传 `(type,ti,idx)`（HTML:1527-1532）。`_collapse_empty_tracks`（main.py:585）或另一进程插/删轨后 `ti/index` 漂移 → 打点/改遮罩/绑特效命中错段。特效 clip 绑定 `target={type:"clip",track,ti,si}`（main.py:4252）无 id。
- **证据**：`02 P4`、`02 P8`、`03 D1-01`、`03 D1-02`、`07 P0-1`；`player.js:50` 与 `edit-context.js:28` 的 key 都是 `"type:ti:idx"`。
- **不修的后果**：**AI 无法稳定表达"给这个片段打点/加特效"**——AI 可控性（当前最高分项）被这个隐患架空；用户"打点消失/值乱跳"。也是 Resource Graph 的硬前提（v2 §3.5 明确阻塞）。
- **修的风险**：改动面最广（后端写方法 + MCP 签名 + 前端 27 个模块），但**兼容优先**可控制：所有方法保留位置参数、新增 `seg_id` 首选，逐个模块迁移，每步跑 `tools/graph_consistency.py` 对拍。07 报告已给出该策略。

### R5 🔴 写盘失败被当成功 + 导入/导入剪映无回滚：静默数据丢失
- **风险描述**：`save_state` 失败返回 False（main.py:1084/1090），但 `add_keyframe`/`set_segment_volume`/`set_segments_props` 等 **20+ 处不检查返回值**仍返回 `{ok:true}`（main.py:3006 例）。`import_media_by_paths`（main.py:4760）部分成功部分失败无回滚；`import_jianying_project`（main.py:4819）在 `state["draft"]=out` 之后才 save_state，中途异常把"半成品草稿"留在内存。
- **证据**：`05 C-101`、`05 C-102`、`05 C-103`；`01 §5.1` 前端 25+ 处写操作直连 API。
- **不修的后果**：磁盘满/权限变更时，用户看到界面更新（内存态）、重启后全部回滚、undo 也无效——**最隐蔽的数据丢失**。
- **修的风险**：建议在 execute 层统一兜底（`save_state` 返回 False → 命令整体回滚 + 返回 `{ok:false}`），改动集中在 CommandManager，一处改全局受益，风险低。

### R6 🔴 事务原子性失效：AI 批量操作半成品 / abort 误回滚
- **风险描述**：① `CommandService.withTx`（property/command.js:25-43）**不检查 beginTx 的 `{ok:false}`**（已有进行中事务时 fn() 照跑，命令在事务外逐条入栈）；② 事务内前端 `Promise.all(jobs)` 并行发命令（HTML:2211），每条 execute 都先 `_reload()`（main.py:2483）读磁盘旧基线 → 后执行者覆盖先执行者；③ `_abort_tx`（main.py:997-1002）恢复 begin 时全量快照并**立即写盘**，若事务是 MCP 开的且卡了 30s（`_TX_TIMEOUT_S=30`，main.py:915），abort 会清掉桌面在这 30 秒内的全部新改动。
- **证据**：`05 D-101`、`05 D-102`、`05 A-102`、`05 A-104`；`01 §5.3` P3-4。
- **不修的后果**：AI 多步操作中途失败留半成品、undo 变成 N 步、误回滚用户改动——**AI 批量能力在原子性上不可靠，V2"一次 undo 撤销整个 AI 操作"的承诺无法兑现**。
- **修的风险**：中。`withTx` 加 begin 检查 + 事务内 execute 跳过 `_reload` + abort 前磁盘 diff，三处改动，前端 command.js 与后端 CommandManager 各一处。

### R7 🔴 变速 ≠1 时预览播放换算自相矛盾
- **风险描述**：不变量 `(src_end - src_start)/speed == duration`（playback-graph.js:44-50）成立，但视频 `PlayerManager.seek`（media.js:467-489）`t = srcStartUs + localUs` **未乘 speed** 且无 `playbackRate`；音频 `AudioEngine.tick`（audio-engine.js:188-191）`elapsed = (playheadSec - c.startUs) / speed`——**方向反了**（正确应为 × speed）。
- **证据**：`02 P2`（🔴）；`media.js:467-489`；`audio-engine.js:188-191`。
- **不修的后果**：speed≠1 的素材预览音画与时间轴错位；导出（pyJianYingDraft 正确支持 speed）与预览不一致——"预览对、导出错"的经典陷阱。剪映草稿导出后用户会看到与预览不同的成片。
- **修的风险**：低。把换算收敛到单一函数（`deriveSrcEndUs` 升级为统一换算器），前端 player/media/audio-engine 三处 + 对拍脚本验证。

### R8 🔴 500ms 轮询 + 全量重建：性能与交互 bug 的根
- **风险描述**：`setInterval(500)` → `refresh()` → `get_state` 全量拉取 → `renderAll` 全量重建（HTML:3362/3262）；`renderTimeline` 每 0.5s 删除全部 `.track/.seg` 再重建（timeline.js:491-603）；`renderSliceMode:"legacy"` 双跑（store.js:77/125）让每个 `Store.set` 都触发全量 `_emit`。为对抗轮询副作用累积 4 个锁/开关（`blocksRefresh`/`_suppressPanelRender`/`_kfEditing`/`_kfDragActive`）。
- **证据**：`03 D2-01`、`03 D6-01`、`03 D6-02`、`03 D6-05`、`05 E-101`、`04 P-016/P-017/P-018`。
- **不修的后果**：每 0.5s O(N) DOM 重建，中大型草稿卡顿；轮询期间面板冻结导致按钮"点不动"（HTML:1241-1249 注释自述）；任何新交互都要先理解全部守卫链才能安全加功能。
- **修的风险**：中。这是"牵一发动全身"的改造，但**可分层**：先做 version 门控（改动最小、收益最大），再做 slice 切换，最后做差量渲染。每层独立验证。

### R9 🟠 双真源数据模型：params vs legacy 镜像漂移
- **风险描述**：Property Kernel 宣称 `seg.params[path]` 是唯一真相源（property-kernel.js:8），但 `setProperty` 写 params + `LEGACY_MIRROR` 镜像（property-kernel.js:71-76）；后端 `update_segment_transform` 只写 `seg.transform`（main.py:2918-2922）、导出只读 legacy 字段（main.py:1528-1542）→ **params 在 refresh 后即丢失**，两端靠 9 处散落的镜像逻辑兜底。
- **证据**：`02 P3`、`04 P-022`（"最重债务"）、`04 P-010`（三套合并容差）；`property/preview-coordinate.js:7` `mode:"legacy"`。
- **不修的后果**："拖的时候改数值"类 bug 复发（main.py:2989 注释自述曾误改 v）；任何直接读 params 的代码刷新后读到 undefined；新加属性要同时维护三张表。
- **修的风险**：高，因为**前端 21 个 property JS + 后端持久化/导出都要动**。建议放 M5（delete 历史补丁阶段）与特效 KF 统一一起做，避免中途破坏现有预览。

### R10 🟠 同步 ffmpeg/Whisper 阻塞 + MCP stdio 卡死
- **风险描述**：`_extract_audio_peaks`（timeout=90）/`toggle_source_audio`（timeout=120）/`_decrypt_jianying_media`（timeout=600）全是同步 subprocess；`transcribe_media`（main.py:4410）faster-whisper CPU 同步推理数分钟。MCP 是 stdio 通道，**调一次 import_jianying_project 整个工具卡死数分钟**；桌面 `_ensure_video_thumbnails`（main.py:5169）在 main() 启动时同步执行阻塞窗口。
- **证据**：`03 D5-01`、`04 P-006`、`05 C-105`（ffprobe 失败静默降级占位时长）。
- **不修的后果**：长视频导入冻结 UI；AI 调转写/解密类命令时 MCP 超时重试（Agent 侧可能重复执行）；启动慢。
- **修的风险**：中。建最小任务队列（threading + task_id + 状态登记）不改命令语义，js_api 写方法改成"提交任务返回 task_id"，前端轮询任务状态。**此风险放 P1 是因为它不动正确性、只动体验与并发安全**，但 MCP 卡死会间接触发 R6 的事务超时，需在 M2 事务修复时同时处理超时宽容。

## 三、修复优先级排序（必须修 / 可以延后 / 不要修）

### 3.1 必须现在修（P0 —— 不修则未来必炸）

| 优先级 | 事项 | 对应风险 | 理由（为什么必须现在） |
|---|---|---|---|
| P0-1 | **id 引用收口（D1）** | R4 | 所有 AI 引用稳定性的地基；阻塞 Resource Graph；改动面最大所以要最早开始，兼容优先逐步迁移 |
| P0-2 | **delete_material 引用检查修复** | R2 | 不可逆文件丢失，一天不修就一天有概率触发；改动 10 行内 |
| P0-3 | **Command 闭环：args + 双轨收敛** | R3 | redo 重放、OperationLog、协作广播全靠它；audit_log 无 args 已让"谁改了什么"护城河失效 |
| P0-4 | **跨进程写竞态：乐观锁 + MCP 串行化** | R1/R6 | 数据安全级；与 P0-3 一起改后端 CommandManager，一次动刀 |
| P0-5 | **写失败可见化 + 导入回滚** | R5 | 静默丢数据比丢数据更可怕；改 execute 层一处全局受益 |
| P0-6 | **变速换算统一（P2）** | R7 | 预览≠导出是"等出事故"的结构；改动小收益确定 |
| P0-7 | **事务原子性三修** | R6 | AI 批量能力的前提；withTx 检查 + 事务内不 reload + abort diff + 超时可续期 |

> 判据：**只改数据模型/命令链/保存语义，不新增产品功能**。P0 做完，用户感知不到新功能，但"数据不再丢、引用不再漂、undo 不再漂移"。

### 3.2 可以延后（P1 —— 做完 P0 再动）

| 事项 | 对应风险 | 延后理由 |
|---|---|---|
| 事件驱动去轮询（D2） | R8 | 轮询是"功能正确、性能差"，不是"会丢数据"。P0 阶段动它风险大（牵动全部前端渲染）；P0 完成、undo/引用稳了之后再改，回归面可控 |
| 数据版本控制 schemaVersion（P0-4 07报告） | — | 独立可做，但收益要等 Document Protocol 才显性；先立字段不阻塞 |
| 删除历史补丁/双真源收敛 | R9 | 属于"清理"不是"止血"；前 5 个锁的清理依赖事件驱动先落地 |
| 时间统一（D3，渐进） | — | 内部先统一换算函数，导出换算不动，低风险可随时做 |
| 动画模型升级（D4 bindings+channels） | — | 读取层兼容先行可独立做，写入层升级放 P1；前提是 P0-6 变速换算先统一 |
| 同步 ffmpeg 异步化（D5） | R10 | 体验与 MCP 超时问题；但 M2 事务修复时需同步做"事务超时可续期"缓解 MCP 卡死 |
| MCP studio_read 迁根目录读新结构 | 02 P6 | AI 读类工具当前读空/报错，独立可修，但影响面在 AI 侧（非用户侧），可排在 P0 后立即做 |

### 3.3 不要修（明确"不做什么"和为什么）

| 事项 | 为什么不做 |
|---|---|
| **不重写渲染为 Canvas/WebGL** | 当前 DOM 合成 + pyJianYingDraft 导出的"预览=导出对拍"是**功能正确的**；渲染架构改造（Render Graph）是 V2 的 ⑧ 系统，P0/P1 阶段动它是用"正确性"赌"未来扩展性"。等 V2.5 稳定后再以"导出侧 Pass 化"渐进推进 |

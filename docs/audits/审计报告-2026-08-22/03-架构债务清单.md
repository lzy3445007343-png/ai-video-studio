## D1 数据引用债（位置索引 vs 稳定 ID）

### D1-01 位置索引 key（"type:ti:idx"）仍是前端主引用
- **位置**：player.js:45-70 `resolveHits`（`key: "video:0:" + idx`）；timeline.js:120-160 `draftSegs`/`segById`；HTML:1707-1712 `findSegByKey`（`key.split(":")` → `segs[+idx]`）；HTML:886 `findSeg`；store.js:49 `selectedKey: "type:ti:idx"`。
- **原因**：早期按 OpenCut 数组模型设计，段定位直接落在轨道数组下标上；稳定 id 是后补的（A 方案）。
- **当前影响**：任何一次 `_collapse_empty_tracks`（main.py:585，空轨折叠）或 `_insert_track`/`delete_*_track`（main.py:503/4019/4052/4076）都会让 track_index 漂移；段删除/移动后 idx 也漂移。前端虽引入 `selectedSegId`（HTML:1714-1719 优先按 id），但 `findSegByKey`、时间轴 hit 命中、KF marker 定位仍大量走 idx；跨轨 drag 传 `trackTidOf()`（timeline.js:335）做缓解，但 `update_effect`、`set_track_meta`、`set_mask` 等仍纯靠 (ti,idx)。
- **风险等级**：高。位置漂移是"段定位错位/操作到别的段"的根源风险。
- **建议处理方式**：分两步：(1) 前端统一 `findSeg(key)` 内部先按 `selectedSegId`/seg 的 `id` 反查，key 仅作显示用途；(2) 后端所有写方法补齐 `segid` 参数并设为首选（move/trim/split/remove 已部分具备，`update_effect`/`update_sticker`/`set_mask`/`set_track_meta` 需补），最终让 (ti,idx) 退化为日志/调试参数。

### D1-02 overlay 混排池按类型计数推导 ti
- **位置**：main.py:371-384 `_overlay_index`（对 overlay 数组按 `tr.get("type")==track_type` 计数 → ti）；main.py:408-429 `_track_by_tid`（同类计数）；playback-graph.js:163-167 `_typeTiOf`；player.js:53-61（`typeCount` 计数）。
- **原因**：overlay 是 text/sticker/effect/video 混排池（数组顺序=z 序），但外部命令用"类型内序号 ti"，必须在访问时实时计数换算。
- **当前影响**：同一 overlay 下标在不同函数里推导 ti 的语义不一致（video 从 1 起、其他从 0 起，`_overlay_index` 与 `_track_by_tid` 的计数起点不同）；跨段/换轨后计数结果依赖遍历顺序，脆弱。`track_tid` 缓解但未全量接入。
- **风险等级**：中。
- **建议处理方式**：建立"类型内 ti ↔ overlay 下标"的单一映射函数并集中测试；或彻底引入 `trackKey = "type:" + tid` 作为命令参数，淘汰 ti 语义。

### D1-03 段 id 不变量依赖人工遵守
- **位置**：main.py:1124-1134 `_ensure_seg_ids`（加载时补 uuid）；main.py:1103-1105 注释"深拷贝生成新段处必须重发 id"；main.py:3325 `duplicate_segment`、3803 `split_segment`、3382 `paste_from_buffer` 均需手动重发 id。
- **原因**：波纹引擎（main.py:1747 `compute_ripple_adjustments`）依赖 before/after 两帧间段 id 配对；id 生成分散在各操作实现里，是纪律而非机制。
- **当前影响**：若某新路径（如 import_jianying_project、AI 插入段）漏发 id，波纹 diff 会错配（同 id 段被当成同一段 → 错误平移）。
- **风险等级**：中。
- **建议处理方式**：把"生成新段"收拢到一个工厂函数（`_make_seg(...)` 统一发 id + 默认字段），所有创建点改走工厂；`_ensure_seg_ids` 保留兜底。

## D2 事件系统债（轮询/全量刷新替代事件订阅）

### D2-01 前后端同步依赖 500ms 轮询
- **位置**：HTML:3362-3367 `setInterval(..., 500)` → `refresh()` → `call("get_state")`；main.py:4990-5012 `get_state` 每次都 `load_state()` 从文件重读。
- **原因**：桌面窗口与 MCP 是独立进程，唯一共享介质是 draft_state.json；为让"人和 AI 实时互看"，选择了最简单可靠的轮询。
- **当前影响**：每 0.5s 全量读盘+全量渲染；为对抗轮询副作用累积了 4 个锁/开关（`InteractionManager.blocksRefresh` interaction-kernel.js:70、`_suppressPanelRender` HTML:1257、`_kfEditing` HTML:3227、`_kfDragActive` HTML:3233）；轮询期间面板重建被冻结，导致按钮/输入框偶发"点不动"（HTML:1241-1249 注释自述）。
- **风险等级**：高。轮询是全量重绘链路的直接推手，也是多个交互 bug 的诱因。
- **建议处理方式**：引入事件推送（本地 WebSocket 或 pywebview 的 `window.pywebview.api` 回调 + 后端主动 push），或至少把轮询降级为"只读 version，变化才拉全量"（`get_state` 支持 `since_version` 参数，无变化返回空）。短期可把 500ms 提到 1000ms + version 门控。

### D2-02 Store 订阅双跑（legacy 全量 `_emit` + slice）
- **位置**：store.js:77 `renderSliceMode: "legacy"`；store.js:125 `if (this.renderSliceMode !== "slice") this._emit()`；HTML:1254 `Store.subscribe(renderAll)`。
- **原因**：slice 迁移是 ADR-2026-08-20 的增量改造，采用"legacy 双跑对照期"策略，尚未切到 slice。
- **当前影响**：任何 `Store.set({playheadUs})` 都会触发 `_emit()` → 全量 `renderAll`（素材面板/时间轴/预览/技能/面板全部重建）。切片订阅被全量广播稀释，性能优化目标未达成。
- **风险等级**：中。
- **建议处理方式**：明确迁移计划，把依赖清单（HTML:3292-3300 注释已列出各渲染函数的切片依赖）逐一核对后切换到 `renderSliceMode="slice"`；删除 `renderAll` 的全量订阅，保留其作为 debug/导入/MCP 批量路径的显式调用。

### D2-03 MCP 心跳用 3s 文件轮询写
- **位置**：mcp_server.py:340-347 `_heartbeat` 线程每 3s `save_mcp_state`。
- **原因**：桌面需要感知 MCP 存活；stdio 进程无法反向推送，只能落文件。
- **当前影响**：mcp_state.json 每 3s 写盘；main.py:5009-5011 特意把 version 与心跳解耦（避免前端每 3s 重渲染）——说明该设计已带来过副作用。
- **风险等级**：低。
- **建议处理方式**：可接受；后续若引入推送通道，MCP 状态也走同一通道，废弃心跳文件。

## D3 时间系统债（时间单位统一）

### D3-01 微秒/毫秒/秒三套单位并存
- **位置**：
  - 微秒：草稿全部段字段 `start/duration/src_start/src_end/src_full`（draft_state.json:29-33 实测 33800000=33.8s）、KF `t`（main.py:2936 add_keyframe 参数 time_us）、特效 `start_us/duration_us`（main.py:4228）、前端 `playheadUs`（store.js:53）、书签 `us`（main.py:3171）。
  - 毫秒：`version = int(time.time()*1000)`（main.py:1062）、mcp_state `updated_at`（mcp_server.py:344）、`_waitSeekSettled` 的 `setInterval(...,80)`（player.js:215）。
  - 秒：AudioContext `ctx.currentTime`（audio-engine.js:59 `_anchorNow` = currentTime - playheadUs/1e6）、LOOKAHEAD_SEC/PAST_SLACK/TICK_MS（audio-engine.js:30-32）、ffprobe 时长秒（main.py:2081 `_video_duration_sec`）。
- **原因**：后端建模选微秒（对齐剪映），前端播放器用秒（Web Audio/DOM currentTime 原生单位），`version` 用毫秒做时间戳，三个来源分属不同层，换算靠 `/1e6`、`*1000` 散落各处。
- **当前影响**：换算点遍布（至少 20+ 处），任何一处漏换/错换都会产生"错位播放/错误打点"类 bug；`_frame_snap_us`（main.py:1416）用 `33333` 硬编码帧长，JS 侧用 `Math.round(1e6/30)`（HTML:2181、edit-context.js:24），舍入语义略有差异（后端 `(t+16666)//33333*33333` 与前端 `Math.round(t/33333)*33333` 边界不一致）。
- **风险等级**：高。
- **建议处理方式**：(1) 定一个"内部唯一单位"（建议微秒），所有跨层边界只允许在 3 个转化点换算（store↔player、audio-engine 锚定、渲染器像素）；(2) 提供单一工具 `usToSec/usToMs/secToUs` 并强制使用；(3) 帧长常量统一为 `1e6/30` 的同一表达（后端也读常量，不写 33333 字面量）。

### D3-02 播放头 vs 媒体时钟双时钟（墙钟/媒体时钟仲裁）
- **位置**：player.js:20 `mediaClockReady` 门控；player.js:383-391（"playTick 立即启动墙钟，媒体是 follower"）；player.js:403-409 drift 节流；audio-engine.js:58-60 `_anchorNow` 实时锚定（取代旧的 `setAnchor` 一次性锚定 audio-engine.js:64-70，函数仍保留）。
- **原因**：WebView2 媒体 `currentTime` 在 paused/seek 时不可靠（代码注释多处自述），被迫引入墙钟仲裁 + 实时锚定。
- **当前影响**：双时钟仲裁逻辑复杂（RECOVER_CAP/跨段 Round D 等状态机，player.js:91-105），`setAnchor`/`timelineToCtx` 旧一次性锚定函数成为死代码残留，新读代码的人容易误用。
- **风险等级**：中。
- **建议处理方式**：删除 `setAnchor`/`timelineToCtx` 死代码，统一到 `_anchorNow`；把"时钟选择仲裁"抽成单一函数，明确两个来源（performance.now 墙钟 / el.currentTime）的信任规则表。

## D4 动画模型债（关键帧数据模型）

### D4-01 关键帧是 keyframes[path] 单层 + legacy 双命名，未形成统一 channel 层
- **位置**：main.py:1372-1390（`seg["animations"] = { path: {"keys":[...]} }`，KF_PROPS 同时含新路径 `"transform.positionX"` 与旧名 `"volume"`）；property-kernel.js:55-57 `LEGACY_CHANNEL`（`"audio.volume"→"volume"`）；playback-graph.js:117（audio clip 的 `segAnim` 直读 `seg.animations`）。
- **原因**：C1 Property Kernel 设计了"params 静态层 + animations 通道层"双层（binding 前身），但后端数据模型与前端旧读法仍是 `animations[path]` 单层 + `volume/speed` 旧字段双轨。双层是"前端读取时的逻辑层"，不是数据层。
- **当前影响**：同一属性存在三条读取路径（`seg.params[path]` / `seg.animations[path]` / `seg.volume` 等 legacy），property-kernel.js LEGACY_MIRROR 做单向镜像才能兜住后端/导出；KF 面板用 `animations[path]` 判断 `isAnimated`，而 `update_segment_transform` 写静态值时同时改 params+legacy，两套写入互有漂移风险（"拖的时候改数值"类 bug 的温床，main.py:2989 注释自述曾误改 v）。
- **风险等级**：高。
- **建议处理方式**：把 C1 双层协议升级为**数据层**统一模型——`seg.props`（静态）+ `seg.channels[path]`（KF 通道）替代 `params/animations/legacy 三份`，导入/迁移一次性把旧字段折叠进 props；KF_PROPS 去掉 `"volume"` 旧名，统一为 `"audio.volume"`（LEGACY_CHANNEL 过渡后删除）。

### D4-02 特效关键帧是另一种扁平格式（第四种时间/数据结构）
- **位置**：effects.js:43-72 `effectParamAt`（`[{param, time, value, easing}]` 扁平数组，time 是相对特效段起点的 us）；main.py:4236 add_effect 的 keyframes 参数同格式；与段级 `animations[path].keys` 完全无关。
- **原因**：特效 DSL 独立演进（effects.json 单一真源），没有并入统一 KF 通道模型。
- **当前影响**：系统内关键帧有 2 套数据模型（段通道 vs 特效扁平数组）、且特效的 easing 字段预留未用（effects.js:63 注释"v1：线性；easing 留作后续"），导出端 `_apply_keyframes_to_segment`（main.py:1653）只处理段通道，特效 keyframes 目前仅预览端吃。
- **风险等级**：中。
- **建议处理方式**：中期把特效参数曲线迁移到统一 channel 模型（或显式声明特效 KF 是"参数包络"不同于"变换动画"，并补导出映射），至少把 easing 要么实现要么从文档中移除。

### D4-03 动画裁剪/插值逻辑双端对拍，但仅靠对拍脚本维持
- **位置**：main.py:1574 `_kf_interp`、1594 `resolve_kf_value`、1631 `_clamp_animations_to_duration`（trim 时裁剪 KF）；HTML 侧 `kfVal`（内联）；tools/graph_consistency.py 对拍 `_playback_graph` 与 playback-graph.js。
- **原因**：预览（JS）与导出（Python）需要同一插值结果，靠手工逐字段对齐 + 对拍脚本守护。
- **当前影响**：新增插值类型（easing/bezier）必须双端同步改，漏改即"预览对、导出错"。
- **风险等级**：中。
- **建议处理方式**：将插值内核提为单一实现（Python 侧生成 JS 常量表，或走 wasm/共享 JSON 描述），把对拍脚本纳入 CI 门禁。

## D5 媒体处理债（ffmpeg/媒体处理）

### D5-01 全部 ffmpeg/ffprobe 为同步 subprocess，且部分在 js_api 调用路径上
- **位置**：`_extract_audio_peaks`（main.py:2341-2345 subprocess.run timeout=90）；`toggle_source_audio`（main.py:2725-2728 timeout=120）；`_has_audio_stream`/`_video_duration_sec`/`_audio_duration_sec`（timeout=20）；`transcribe_media`（main.py:4426-4447，faster-whisper 同步 CPU 推理）；`get_media_duration`/`get_media_dimensions`（main.py:1898/1918）。
- **原因**：初始为单进程桌面工具，同步最简单；ffmpeg 探测类调用量小可容忍，但抽音轨/波形/Whisper 属于重任务也被同步塞进 API。
- **当前影响**：
  - 素材导入（`import_media_by_paths` main.py:4760 / `drop_files` main.py:5057）里同步算 peaks，长视频导入阻塞整个 js_api 调用；HTML:2906-2907 注释"pywebview 主线程执行会冻结 UI"，需用 setTimeout 先画遮罩再发起阻塞调用。
  - 转写可能数分钟，无进度回调、无取消、无任务队列，期间前端只能显示"识别中"且该 call 占住。
  - `_ensure_video_thumbnails`（main.py:5169）在 main() 启动时同步执行（main.py:5203），多素材冷启动阻塞窗口显示。
- **风险等级**：高。
- **建议处理方式**：建最小任务队列（threading + 状态登记进 draft_state 或独立 task.json），js_api 写方法改成"提交任务返回 task_id"，前端轮询任务状态；转写/抽音轨/波形三处优先迁移。启动缩略图改后台线程。

### D5-02 媒体服务为单本地 HTTP 服务器 + Range，无缓存失效策略
- **位置**：main.py:69-199 `_SilentHTTPRequestHandler`（_parse_range 93、_serve_file 117、_local_abs_path 172）；媒体 URL 经 fileURL（HTML:823-837）走 `/local/` 代理。
- **原因**：WebView2 不能读 file:// 播视频，必须走 http；零拷贝直读源文件。
- **当前影响**：功能正确；但 `/local/` 暴露任意绝对路径读取（HTML:827-828 encodeURIComponent 后拼接），是**信息暴露面**——任何能打开该页面的人可读任意本地文件（桌面工具内可信，但需知晓）。无磁盘缓存层，重复 seek 依赖 WebView2 自身缓存。
- **风险等级**：中。
- **建议处理方式**：至少对 `/local/` 做路径白名单前缀校验（assets/、extracted_audio/ 等）；长视频加服务端缓存头策略评估。

### D5-03 AudioEngine 解码无全局并发上限（除 inflight 去重）
- **位置**：audio-engine.js:98-131 `_decode`（bufferCache LRU 上限 8，`_decodeInflight` 去重）。
- **原因**：lookahead 2s 调度需要提前 decode；inflight 去重只防同一路径并发，不限制不同路径并发数。
- **当前影响**：多段音频短区间密集切换时可能同时发起多个 decodeAudioData，内存尖峰；Web Audio 单 ctx 下大量 BufferSource 并发。
- **风险等级**：低。
- **建议处理方式**：加信号量（并发 decode 上限 2~4），失败降级跳过。

## D6 UI 渲染债（全量刷新 / 状态订阅粒度）

### D6-01 renderTimeline 每次全量销毁重建 DOM
- **位置**：timeline.js:491-603 `renderTimeline`（`[...content.querySelectorAll(".track, .seg")].forEach(e => e.remove())` 后整轨重建）；renderAll（HTML:1231-1253）→ renderTimeline。
- **原因**：vanilla JS 从单 HTML 演进，无组件 diff/复用；对齐 OpenCut 的组件模型只停留在注释层。
- **当前影响**：每次 Store.set 或 500ms 轮询都销毁重建时间轴 DOM：滚动位置需手动保存恢复（timeline.js:495-496/588-589）；DOM 事件监听全部重建；拖拽中播放头/选中的"瞬时状态"要靠额外恢复逻辑（HTML:601 refreshKfMarkerSelection）。渲染期间若用户正在点击，click 可能被吞。
- **风险等级**：高。
- **建议处理方式**：改"keyed 差量更新"——只对新增/删除/移动的段做 create/move，段 DOM 与 seg.id 绑定（element.dataset.segId），同段仅更新位置样式；播放头/标尺独立轻量更新。

### D6-02 500ms 全量 get_state + 显式 renderAll 双全量
- **位置**：HTML:3362-3367（轮询）→ HTML:3218-3267 `refresh` → HTML:3262 `renderAll(Store.state)`；get_state 返回全量 materials+draft（main.py:4990）。
- **原因**：见 D2-01；C4.4 注释"slice 模式下 set 不广播，refresh 若靠 _emit 会白屏"——为兼容未完成迁移而显式全量。
- **当前影响**：每 0.5s 解析全量 JSON（含波形/缩略图路径映射重建 thumbMap/waveMap HTML:3240）+ 全量渲染 6 个面板区域；中大型草稿下 UI 线程明显压力。
- **风险等级**：高。
- **建议处理方式**：与 D2-01/D6-01 一起做增量：get_state 支持增量（只回 draft 变化部分），refresh 只渲染变化切片；缩略图/波形 map 缓存进 Store 不重建。

### D6-03 预览渲染器每帧做命中扫描 + 元素状态机，但复用层脆弱
- **位置**：renderer.js:110-284 `renderPreview`（每帧 resolveHits 后对每轨建/复用元素，`previewState.visualEls` 双槽预加载 preloadNextVideoSlot 335-406）；player.js:45 `resolveHits` 每帧遍历全轨。
- **原因**：播放与预览需要"当前命中段"的即时响应，选择每帧全扫。
- **当前影响**：`resolveHits` O(段总数) 每帧执行（RAF 60fps）；preview-drag.js:78-83 注释自述 `previewState.visualEls` 的 rec.key 可能 stale（段已删但 wrap 残留无清理路径）——复用层存在悬挂引用风险，靠 commit 前 findSegByKey 防御。
- **风险等级**：中。
- **建议处理方式**：`resolveHits` 用段表排序 + 二分/区间树代替全扫；renderPreview 的元素池在段删除/轨道折叠时显式销毁（统一清理入口）。

### D6-04 多面板全量重建 + 冻结开关绕行
- **位置**：HTML:1247-1249（`_suppressPanelRender` 时跳过 showToolTab）；renderPropertyPanel（HTML:1303-1351 面板切换即重建）；audio/speed/mask/effect 各 panel render 函数每次全量 innerHTML。
- **原因**：属性面板在 500ms 轮询下每 0.5s 推倒重建，为保住按钮交互加了冻结开关，又因冻结导致"按钮点击后状态不同步"需要 showToolTab 手动恢复（HTML:1282-1285）。
- **当前影响**：面板渲染被轮询与用户动作两条路径竞争管理；`_suppressPanelRender` 为全局可变状态，容易漏置/漏清。
- **风险等级**：中。
- **建议处理方式**：面板改为组件复用（Value 只更新 input.value/控件状态，不重建 DOM 树）；去掉全局冻结开关，改为"面板在收到对应 slice 变更时才更新"。

### D6-05 渲染/刷新路径上的锁与开关蔓延
- **位置**：HTML:3221 `InteractionManager.blocksRefresh`、HTML:3227 `_kfEditing`、HTML:3233 `_kfDragActive`、HTML:3363 `!Store.state.drag`、HTML:1257 `_suppressPanelRender`。
- **原因**：每个"轮询干扰交互"的 bug 都加一个前置判断，形成累积的守卫链。
- **当前影响**：守卫链互相耦合（如 `_kfDragActive` 与 `refresh()` 的补刷时机、`notePendingRefresh` 与 commit 的重复补刷 HTML:141），新交互必须理解全部守卫才能安全加功能；守卫漏开/漏关直接导致 UI 卡死或数据回弹（HTML:2151 注释"锁是否正常释放——只 lock 无 unlock → 锁死"）。
- **风险等级**：中。
- **建议处理方式**：把"刷新抑制"收敛为单个 RefreshGate 状态机（谁在交互/谁在编辑/谁在拖 KF 统一登记），由它决定 refresh 是否放行，替代散落的 if 判断。

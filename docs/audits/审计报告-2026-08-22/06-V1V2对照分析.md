### 0.2 当前系统一页纸架构（先测量，再对照）

```
用户手势（DOM 事件）
   │  InteractionManager（property/interaction-kernel.js，GestureSession 状态机）
   ▼
CommandService（property/command.js）── pywebview bridge ──► main.py Api.execute(cmd_id, args, meta)
   │                                                              │
   │  beginTx/commitTx/abortTx ────────────────────────────────────┤ CommandManager.execute（整轨快照）
   ▼                                                              ▼
500ms 轮询 get_state（工作台v0.8时间轴.html:3362）          draft_state.json（唯一真相源，单文件全量）
   │                                                              │
   ▼                                                              ▼
Store.set({draft}) → renderAll（全量 DOM 重建）              save_state() 立即写盘 + 读回验证
   │                                                              │
   ▼                                                              ▼
renderPreview（DOM 合成层）+ playTick（rAF 墙钟）           export_draft() → pyJianYingDraft（剪映 JSON）
```

**六个结构性事实（决定后续所有差距评价）**：

1. **数据源 = 单文件 `draft_state.json`**（`main.py:load_state/save_state`）。前端 500ms 轮询 `get_state()` 拉全量（`工作台v0.8时间轴.html:3362`），`refresh()` 再 `renderAll()` 全量重建 DOM（`:3262`）。→ 对应圣经 v2 债务 **D2（轮询 + 全量订阅）**。
2. **段定位 = 位置索引 `(type, ti, idx)`**，贯穿 MCP 工具签名（`mcp_server.py:86 remove_segment(track_type, track_index, index)`）与前端 key `"video:0:2"`（`player.js:50`）。→ 对应圣经 v2 债务 **D1（位置索引）**。
3. **动画 = 扁平 `seg.animations[path].keys`**，key 字段 `{id, t, v, seg}`（`draft_state.json:35` / `main.py:1372` 注释自述"与 OpenCut 差异"）。→ 对应圣经 v2 债务 **D4（扁平 keys）**。
4. **时间 = 普通 int 微秒**（`seg.start`/`duration` 单位 µs），无品牌类型、无整数 tick 常量、无 FrameRate 结构（导出固定 30fps，`main.py:4580 create_draft(name,W,H,30)`）。→ 对应圣经 v2 债务 **D3（float 微秒）**。
5. **渲染 = 前端 DOM 合成 + Python 剪映导出两套独立实现**，中间靠 `playback-graph.js buildPlaybackGraph` ↔ `main.py _playback_graph` 逐字段对拍（`playback-graph.js:9-10`）。→ 不存在圣经 v1 的"scene-builder → node tree → resolve"单一声明的渲染管线。
6. **保存 = 每次操作立即写盘**（`save_state` 无防抖，`main.py:1040`），前端靠轮询反向同步。与 OpenCut `SaveManager` 800ms 防抖（订阅推送）方向相反。

### 1.1 逐项详细说明（V1 对照 · 关键项展开）

**#2 Command 模型 —— "包装型命令"与"自包含命令"的差距**

OpenCut 的命令是自包含对象（`execute()` 自己读写状态、返回 `CommandResult.selection`）；当前系统是**方法包装**：

```python
# main.py:927-953
def execute(self, api, cmd_id, args=None, meta=None):
    fn = getattr(api, cmd_id, None)          # 直接反射到 Api 方法
    cmd = Command(cmd_id, cmd_id, meta)
    cmd.saved_state = copy.deepcopy(api.draft)   # 整轨快照
    result = fn(**dict(args or {}))              # 调方法，方法内部原地改 draft
    ...
    self.history.append(cmd)                     # 只记录 cmd_id + 快照，无重放能力
```

后果：undo 只能整轨还原快照，**无法重放命令**（replay），这对圣经 v2 的 OperationLog 回放、协作广播、AI 回放是硬伤——它缺 `CommandLogRef.args`（`ai-native-架构圣经-v2:653`）。好消息是 `Command.meta.changed_paths`（`main.py:900`）已开始记录改动属性路径，是重放能力的雏形。

**#5 草稿层 —— 有 Overlay，无 previewTracks**

OpenCut 的关键机制是"`getPreviewTracks() = previewTracks ?? activeScene.tracks`，渲染层永远读预览优先"。当前系统没有"双层轨道"概念：

- 拖动期间：`DragSession` 把新值写进 `OverlayState.transforms[segId][path]` + 直接改 `el.style`（`preview-drag.js:49-53`），**不改 Store.state.draft**；
- 松手：`withTx` 提交后端，`refresh()` 回填新 draft → `renderAll` 全量重绘。

也就是说"临时态"是**独立的 DOM/overlay 层**而非"正式轨道的投影层"。它达成了同样的目标（拖动不污染历史、松手一次 commit），但丢失了 OpenCut 的"预览优先读取"契约——任何渲染代码必须知道自己在读 overlay 还是正式 draft，而 OpenCut 只有一个入口。这是一个"实现等价但契约更弱"的部分实现。

**#13 渲染 —— 前端 DOM 合成 vs OpenCut 节点树**

OpenCut：`buildScene()` 建 `RootNode` 节点树 → `resolveRenderTree()` 按 time 解析 → Canvas/GPU 后端。当前系统：

- 预览：`renderPreview` 直接创建/复用 DOM 元素（`previewState.visualEls/audioEls/textEls/stickerEls`，`media.js:10-15`），`applyKfTransform` 每帧写 `el.style.transform`（`renderer.js:714-736`）；
- 导出：`export_draft` 用 pyJianYingDraft 逐段生成 `VideoSegment/TextSegment/AudioSegment` + `ClipSettings` 换算（`main.py:1516 _video_clip_settings`）。

**两套实现的换算靠对拍脚本保证**（`playback-graph.js:9` 提到 `tools/graph_consistency.py` 逐字段对拍）。这是当前系统"预览=导出同源"的工程化方案，比 OpenCut 的"单一渲染管线"多一份维护成本，但**语义上是同一目标的两种实现**，不算缺失，算"结构上分叉"。圣经 v2 的 Render Graph 正是要把这两套收成一套 6-Pass 管线。

**#15 保存 —— 方向相反的"即时写 + 轮询读"**

OpenCut：SaveManager 订阅 → 800ms 防抖 → 写 IndexedDB/OPFS。当前系统：每次 execute 立即 `save_state` 写盘（有文件锁 + 读回验证，`main.py:1064-1083`），前端 500ms 轮询 `get_state` 拉全量回填（`工作台v0.8时间轴.html:3362`）。这带来两个代价：

1. **每次操作都全量写 JSON + 全量读 JSON**，数据量大时（百段 + 波形）有性能与竞态风险（虽有 portalocker 锁，但跨进程 read-after-write 仍有窗口）；
2. **前端靠轮询同步，导致"伪实时"**——MCP 进程写入后，桌面最多延迟 500ms 看到，且 `renderAll` 每次轮询全量重建 DOM，必须靠 `_suppressPanelRender` 冻结面板（`工作台v0.8时间轴.html:1256-1258`）来避免"点不动"。

这不是 bug，是**架构选择**：单文件 + 轮询换来了"人和 AI 跨进程共享同一份状态"的简单性（`main.py:4990 get_state` 注释明言）。但它就是圣经 v2 D2 债务的实体。

**#20 AI 通道 —— 当前系统最强资产（超越 OpenCut v1）**

OpenCut 圣经 v1 明确"没有独立 AI API 层，Manager 层就是 API"。当前系统在此基础上**多走了两步**：

1. **统一命令入口 + 审计**：`Api.execute(cmd_id, args, meta)`（`main.py:2477`），meta 含 `actor/reason/confidence/source`，审计可查（`audit_log`）；
2. **MCP Server**：`mcp_server.py` 把 30+ 原子能力暴露成 MCP tools，全部复用 `api.execute`（`_exec`，`mcp_server.py:33`），并提供细粒度读取（`sr.list_tracks`/`get_segment_detail`/`get_material_peaks`），避免把全量草稿丢给 agent。

这是圣经 v2 里"后端 Command API（90+）+ MCP 是 CommandGenerator 的现实宿主"的直接证据，也解释了为什么 v2 说"保留并衔接"。

### 2.1 八大系统逐项展开（雏形/部分实现的具体说明）

**① Document Protocol（雏形 20%）—— 从"快照"到"协议"差什么**

当前 `draft_state.json` 的结构：`materials[] + draft{overlay/main/audio/canvas/_track_meta} + version + meta`。对照圣经 v2 `VideoDocument`（`ai-native-架构圣经-v2:194-205`）：

| 协议字段 | 当前有无 | 说明 |
|---|---|---|
| `schemaVersion` | ❌ | 只有 `version`（时间戳 `main.py:1062`），无协议版本号与迁移器 |
| `metadata` | 部分 | 无 id/name/description/author/orientation/tags |
| `assets[]` | 部分 | `materials[]` 存在，但无 `kind:"url"/"generated"`、无 `status` |
| `timeline` | ✅ | `draft` 即时间线，结构与 OpenCut `TProject.scenes` 相近（但无 scenes 层，只有单场景） |
| `animation` | 部分 | `seg.animations` 内嵌在元素上，无全局动画注册表 |
| `plugins[]/extensions[]` | ❌ | 无 |
| `history` | ❌ | 撤销栈只在进程内存（`CommandManager.history`），不落盘 |

差距本质：当前文件是**内存对象的一次序列化**（`json.dump(state)`），不是**独立定义的协议**（schema 生成类型 + 校验 + 迁移）。AI 生成的任何 JSON 都无法通过"加载→校验→迁移"流程变成运行时状态。

**② Plugin System（雏形 25%）—— 配置真源有了，机制没有**

`effects.json` 已经是"单一真源 + 自描述"（每个特效带 label/params/filters.css/filters.ffmpeg），`_load_effects` 把 css/ffmpeg 模板编译成函数（`main.py:1136-1168`）。这证明"声明式定义 → 双适配器"的路线可行。缺的是：

- **无统一注册 API**：`registerPlugin({manifest, impl})` 不存在；前端 `Effects` 表（`effects.js:29`）靠人工镜像，无法从 JSON 自动生成 css adapter；
- **无命令/面板/exporter 扩展点**：只覆盖 effect 一种能力；
- **无依赖管理/版本**：新增特效 = 手改 JSON + 手写 JS 镜像（`effects.json:2` 注释明说）。

**③ Preset System（缺失 0%）**

整个代码库里搜不到 template/preset/style-pack 概念。最接近的是 `CANVAS_PRESETS`（画幅预设，`main.py:4571` 引用）和 `KF_PROPS`（打点属性表），但都是单一维度的注册表。圣经 v2 的 `PresetDefinition{style, animation, timing, semantic}` 四元组完全空缺。这也解释了为什么当前 AI 只能做"命令级"操作——没有"模板级"的食材库。

**④ Semantic Layer（雏形 15%）**

`bookmarks` 的语义：`Store.state.bookmarks: [{us, name}]`（`store.js:54`），前端 UI 标注（时间轴红点），`main.py:3171-3229` 有完整 CRUD。它是圣经 v2 `StoryBeat` 的**最小子集**（有 time 和 label，无 type/intensity/notes/元素关联）。`transcribe_media`（`main.py:4410`）是本地 Whisper 转写，能产出带时间戳的字幕，是"AI 自动标注"的执行引擎原料，但结果直接变字幕段（`add_subtitles`），**没有进入语义标注通道**。

**⑤ Resource Graph（完全缺失 0%）**

当前唯一的跨对象引用链是：`seg.material_id` → `materials[].uid` → `materials[].path`（`store.js:144 resolveSegPath`、`playback-graph.js:53 _resolvePath`）。这是 `usedBy` 边（asset→element）的**半成品**——能回答"这个素材被谁用"，但定位依赖 `(type,ti,idx)` 位置索引（段 id 存在但未被用作引用）。要建 Resource Graph，必须先完成 D1（id 引用改造），否则图会随轨道重排漂移。

**⑥ AI Intent Layer（雏形 30%）**

现状：`mcp_server.py` 的 tool 直接对应 Api 方法（`add_to_timeline`/`split_segment`/`add_effect`…），参数是"剪辑师级"细节（`track_index`/`at_time_us`/`src_start`）。这就是圣经 v2 说的"AI 直接下发命令"。已具备的意图层原料：

- 统一命令入口 `api.execute`（`main.py:2477`）→ 可升级为 `submitIntents`；
- 审计 meta（actor/reason/confidence/source）→ 已是 `AIIntent.source/confidence` 的字段等价物；
- 事务（begin/commit/abort）→ 已是 `IntentLayer.stage()` 的雏形（批量操作一次 undo）；
- MCP 细粒度读取（`sr.list_tracks/get_segment_detail/get_material_peaks`）→ 是 `Planner` 查库的前置。

**⑦ Collaboration / Event（雏形 20%）**

`CommandManager.audit_log`（`main.py:1034`）只返回 `history` 里的 `{cmd_id,label,meta}`，无 `args`（无法重放）、无版本向量、无时间戳。前端 `Store.subscribeSlice`（`store.js:81-87`）是**同进程**切片订阅，`renderSliceMode="legacy"` 说明还在"迁移对照期"（双跑）。`mcp_state.json` + 3 秒心跳（`mcp_server.py:325-347`）是"桌面知道 AI 活着"的**伪协作**（单向状态通告）。圣经 v2 的"Command 执行时同时发 EditorEvent 到 EventBus 并写 OperationLog"完全未落地。

**⑧ Render Graph（完全缺失 5%）**

圣经 v2 的 6-Pass（video/mask/effect/color/composite/output）对应到当前代码：video/mask/effect 三 Pass 的能力**散在**前端 DOM 合成（`renderer.js`）与 Python 导出（`main.py export_draft`）两套实现里；color（LUT/调色）、ai-enhance、output 全新。`Effects` 表（`effects.js:29`）的"每个 effect_type 一个 preview 适配器"是 Pass 注册的雏形（但只挂 CSS 滤镜，无像素管线）。

## 3. 对照总结（Phase 8 + Phase 9 汇合）

### 3.1 V1 对照一句话结论

**当前系统的命令/事务/草稿/交互四件事已经达到 OpenCut v1 的功能等价（甚至 AI 通道超越），但底座是"单文件 + 位置索引 + 轮询"的自研路线，缺少 OpenCut 的四个结构性保障：不可变替换、预览优先读取、整数 tick、单一渲染声明。** 前者让它"今天能跑、AI 能调"，后者让它"难演进、易漂移"。

### 3.2 结构债与系统缺口对应关系

| 圣经 v2 债务 | 源码证据 | 阻塞的 v2 系统 |
|---|---|---|
| D1 位置索引 `type:ti:idx` | `mcp_server.py:86`/`player.js:50`/`edit-context.js:28` | Resource Graph（⑤） |
| D2 500ms 轮询 + 全量订阅 | `工作台v0.8时间轴.html:3362`/`refresh`→`renderAll` | Event/Collaboration（⑦） |
| D3 float 微秒 | `seg.start` µs/`edit-context.js:24`/导出固定 30fps | Document Protocol（①） |
| D4 扁平 keys | `draft_state.json:35`/`main.py:1372` | Preset（③）动画段、Render Graph（⑧） |
| D5 同步 ffmpeg | `_make_thumbnail`/`_extract_audio_peaks`/`transcribe_media`（同步阻塞） | AI 完整版（⑥） |
| D6 DOM 全量重建 | `renderAll`/`refresh` 每次轮询重建 | Event/协作（⑦） |

### 3.3 当前系统"已超出 V2 预期"的资产（路线图必须保留）

1. **后端 90+ 命令 + 统一 execute + 审计 meta** → Intent Layer 的命令宿主（`main.py:2477`）；
2. **MCP Server 30+ tools + 细粒度读取** → AI Agent 接入点（`mcp_server.py`）；
3. **effects.json 单一真源 + css/ffmpeg 双适配器** → Plugin 系统的天然起点（`effects.json:1`）；
4. **C1 Property Kernel + C2 Interaction Kernel + C3 CommandService + C4 Subscription** 四内核 → 圣经 v2 的 ParamDefinition 注册表 + Controller 层 + Command 总线 + 订阅模型（`property/` 目录）；
5. **EditContext 一次手势一个事务** → 圣经 v2"Transient staging → 一次 commit 一条 undo"的现成实践（`edit-context.js:26`）；
6. **playback-graph.js ↔ _playback_graph 双端对拍** → 未来 Render Graph 的"预览=导出同源"工程基础（`playback-graph.js:9`）。

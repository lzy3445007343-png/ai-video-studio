定调：现在不是在"修 bug"，是在给编辑器补一个能承载 Agent 的底座。根因不是某个函数写错，而是 媒体生命周期被渲染层抢走了所有权。下面两张图把"现在谁拥有什么"和"目标该谁拥有什么"画清楚， 确认无误后再按 Step1→2→3 落地（见 P0重构实施计划v2.md）。

一、当前架构（as-is）：五层都在，但所有权乱了

实情：项目里已经有 Store（数据层）和 call()（MCP 桥）的雏形，不是一锅粥。问题出在 渲染层 越权拥有了媒体生命周期，且 播放层 跨段时回调了渲染层去重建媒体。

核心冲突（一句话）：渲染层 既负责"编辑态结构变更"又负责"播放态跨段"， 而 播放层 跨段时直接调 renderPreview() 全量重建媒体。 这就是"播放期间媒体被杀"的唯一通路。改错层 = 在播放层或渲染层单点打补丁，而不是收口媒体所有权。

二、目标架构（to-be）：五层单向向下，播放层独占媒体

红框"禁止修改区"是这次要立的新铁律：播放进行中，除了 Player 自己的 seek/play/pause/volume，任何层都不得创建/销毁/重建媒体、不得改 src、不得 load()。

四、与 OpenCut 的对应关系（只学骨架，不抄代码）

来源：OpenCut对照诊断报告.md（已分析其 commands/timeline/、update-pipeline、snapping、placement 源码）。下面 5 点逐项对应，结论是我们分层方向已对齐 OpenCut，缺口只在"播放层独占媒体"与"Command 落地"。

设计点OpenCut 怎么解决我们的对应问题该借鉴的原则对齐状态
1. Clip 数据结构element 含 start/duration + 源映射；不可变替换模型segment 已含 start/duration/src_start/src_end（SCHEMA.md）timeline 与 source 永远分离已对齐（I1）
2. timeline/source 换算update-pipeline.ts 的 retime 派生规则集中算散落 us-seg.start 手写（drawAllWaves/_seekMedia）单一换算函数，禁散写Step2 补 timelineToSource
3. 播放媒体生命周期媒体由 playback 独立管理，editor 不重建renderPreview 拥有媒体；playTick 跨段重建(L1544)Player 独占媒体，播放期不死缺口=P-1 Step1 修
4. 状态更新↔渲染execute→updateTracks(整份快照)→派生→渲染解耦Store + renderPreview 混权；渲染顺带拥有媒体状态变更→派生→渲染，三者解耦Step1/3 收口
5. Command/ActionCommand 对象：execute()=整份快照+计算，undo()=回滚call()+_push_undo(deepcopy)；尚未有 Commands 对象Command=变更单元+撤销；UI/Agent 同入口Step3 包 Commands
对照结论：OpenCut 帮我们验证了一件事——根因（P-1）正是"媒体被渲染/编辑层拥有"，这正是 OpenCut 用独立 playback 管理避免的。 所以我们 Step1 不是"抽个漂亮 Player 对象"，而是把媒体所有权从渲染层收口到播放层，与 OpenCut 原则一致。
